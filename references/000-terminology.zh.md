# ProofScaffold 术语规范

> 状态：草案 v0.5，2026-07-19（Prelude 定位收敛：维持极小 pre-logic 现状，扩展为开放问题）。  
> 英文版：[ProofScaffold Terminology](000-terminology.en.md)  
> 适用范围：ProofScaffold 的设计文档、公共 API 文档、代码评审、交换格式规范以及相关中文材料。  
> 本文规定项目内的推荐用语，但不冻结 Python 类名、文件格式名或序列化协议。

## 1. 目的

ProofScaffold 同时涉及数学逻辑、证明助理、编译器、数据交换和搜索系统。相同英文词在这些领域中往往具有不同含义；如果直接保留英文或逐字翻译，容易把下列概念混在一起：

- 数学对象的名称、内容和同一性；
- 证明已经完整形成，与证明已经通过验证；
- 作者层的简写、核心语义对象和后端执行表示；
- 断言允许被使用，与断言已经具有可信实现；
- 内存对象、可交换档案和验证证书。

本术语规范的目标是建立一套稳定、自然且可审计的中英文词汇，使同一概念在文档、API 和讨论中始终保持同一含义。

## 2. 技术背景与体系结构

### 2.1 数学语义层次

```text
形式语言
  决定哪些表达式合法
        │
        v
判断与演算系统
  决定可以作出哪些判断，以及怎样推出新的判断
        │
        v
逻辑系统
  组合语言、演算和逻辑公理
        │
        v
具体理论
  加入领域语言、定义、非逻辑公理和定理
        │
        v
断言接口与证明实现
```

### 2.2 对象的三个表示阶段

```text
规范与声明
  库作者编写的有限事实源
        │ 解析、冲突检查、继承展开
        v
语义接口
  不可变、可摘要、供消费者依赖
        │ 绑定记法、后端、解析器和构建上下文
        v
运行时环境
  支持实际编写、验证和输出
```

这三个阶段不得折叠。运行时对象不是数学内容的标识；显示记法和后端词元也不属于抽象语言的语义内容。

### 2.3 证明的生命周期

```text
ProofAuthor ───────────────┐
                           v
                      完整证明 ─────> 语义验证 ─────> 证明档案
                           │
ProofState <──精化/搜索────┘
                           │
                           └────> 后端转换 ─────> Metamath 等后端
```

普通线性证明由 `ProofAuthor` 编写；交互式证明和搜索使用不可变 `ProofState`。二者最终产生同一种完整证明，并共享同一断言应用内核和最终合法性标准。

### 2.4 四个必须分开的概念

```text
标识符
  如何引用对象

内容摘要
  对象的规范内容是否完全一致

验证结果
  对象是否在特定理论环境和信任策略下有效

证明证书
  可独立保存或传递的验证证据
```

拥有摘要不等于已经验证；同名对象也不等于内容相同。

## 3. 用词原则

1. 中文正文以中文术语为主。代码类型或字段第一次出现时采用“中文名（`CodeName`）”，后文只在必要时保留代码名。
2. 已有稳定数学译名时优先采用通行译名，例如“项、判断、代入、合一、公理、定理、保守扩张”。
3. 一个英文词不必在所有语境中固定为同一个中文词。`artifact`、`identity`、`projection` 等必须按实际含义翻译。
4. `identifier` 译为“标识符”；`digest` 译为“摘要”；`identity` 根据语境译为“同一性、内容一致性或内容标识”，不一律译为“身份”。
5. `validation` 在对象内部形状检查的语境中写“结构检查”；`verification` 写“验证”或“语义验证”。
6. `elaboration` 译为“详化”，`refinement` 译为“证明精化”；二者不得混用。
7. 只有在精确理论环境下完成语义重放后，才能说一份证明“通过验证”。构造成功、结构合法或拥有摘要均不足以作此表述。
8. 对可能进入公共 API 的术语，优先选择能直接说明对象职责的名称，而不是保留内部实现隐喻。
9. `author` 指人时译为“作者”或“证明作者”，`proof authoring` 作为活动译为“证明写作”；只有 `ProofAuthor` 这一明确的软件组件译为“证明编写器”。
10. `global` 在作用域、标识符、唯一性和对象同一性语境中译为“全局”，不译为“全球”或“世界”。

## 5. 第一层：基础架构与表示阶段

本层规定设计文档中描述对象生命周期时使用的基础词汇。

| 英文术语／代码名 | 推荐中文 | 含义或定义 | 在体系中的作用 |
| --- | --- | --- | --- |
| Specification | 规范 | 由库作者编写的有限、声明式数据，用来规定一个对象应包含的内容和约束。 | 作为事实源；应当可检查、可摘要，并避免依赖任意运行时回调。 |
| Declaration | 声明 | 规范中的一个具名语义单元，例如类别、构造子、推理规则、公理或定理声明。 | 提供可以独立引用、检查和组合的最小定义单位。 |
| Interface | 接口 | 声明经依赖解析、冲突检查和继承展开后形成的只读公共视图。 | 供消费者依赖；接口内容由接口摘要固定，不等同于其某个具体实现。 |
| Implementation | 实现 | 满足某个接口的具体内容，例如定理的证明体或一种后端绑定。 | 允许在不改变接口的前提下替换具体实现。 |
| Resolution | 解析与合成 | 检查声明、解析依赖、展开继承并生成不可变接口的过程。 | 把作者层的规范转化为消费者可安全使用的接口；不要与句法解析混称。 |
| Runtime environment | 运行时环境 | 把语义接口与记法、后端、注册表、依赖解析器及构建上下文绑定后的运行时对象。 | 支持实际的解析、构造、验证和后端输出，但不应被当作数学对象的内容标识。 |
| Façade | 简化接口 | 面向普通用户的窄接口，用来隐藏不必由用户直接管理的内部对象。 | 例如 `Theory` 或 `ProofAuthor` 可作为简化入口；中文正文不建议直接使用 façade。 |
| Immutable | 不可变 | 对象一经建立，其可观察状态不再改变；操作通过返回新对象表达变化。 | 为证明分支、缓存、并发和内容摘要提供稳定基础。 |

## 6. 第二层：语言与表达式

本层描述哪些表达式是合法的，以及表达式如何形成；它不规定哪些判断可证。

| 英文术语／代码名 | 推荐中文 | 含义或定义 | 在体系中的作用 |
| --- | --- | --- | --- |
| Formal language | 形式语言 | 由类别、变量种类、构造子和绑定行为组成的有限表达式构造体系。 | 规定“能够写出什么”；是逻辑、理论与证明的语义基础。 |
| Sort | 类别 | 多类别语言或代数签名中对项进行分类的具名成分；每个变量和项具有一个类别，构造子的输入与输出由类别规定。 | 对应代码中的 `SortId`；在代数解释中，每个类别对应一个载体集合。它接近基本类型，但不等同于类型论中一般意义的 `Type`。 |
| Variable kind | 变量种类 | 规定一类变量所属类别及其可参与的绑定行为。 | 使对象变量、公式变量、类变量等在结构上可区分。 |
| Term | 项 | 形式语言中的核心语义表达式，通常由变量项或构造子应用项递归组成。 | 是作者、验证器和交换格式共同操作的表达式对象；显示字符串不是项本身。 |
| Variable term / Application term | 变量项 / 应用项 | 变量项引用一个变量；应用项把一个构造子应用于一组有序参数。 | 对应 `Var` 与 `App`，构成无空缺的核心 `Term` 联合。 |
| Constructor | 构造子 | 具有稳定标识符、输入类别和输出类别的表达式构造规则。 | 定义抽象语法树的节点形状；其显示符号与后端词元不属于构造子的语义内容。 |
| Binder | 绑定算子 | 在某些参数位置引入变量，并规定这些变量在其他参数中的作用域的构造子行为。 | 支持量词等结构，并为自由变量、变量捕获和 α-改名提供依据。 |
| Abstract syntax | 抽象语法 | 不依赖具体拼写、排版和后端词元的结构化表达式表示。 | 确保 `→`、`->` 等不同记法可以指向同一个语义构造子。 |
| Token | 词元 | 句法解析或后端表示中的不可再分词法单元。 | 用于解析和后端输出；词元拼写不等同于构造子的语义标识。 |
| Notation | 记法 | 表达式的输入与显示约定，包括别名、优先级、结合性和标准呈现形式。 | 改善作者体验；记法变化不得改变项或语言的语义摘要。 |
| Parsing | 句法解析 | 把字符或词元序列转换为句法树或语义项的过程。 | 属于记法与前端处理，不应与依赖解析或接口合成混淆。 |
| Rendering | 呈现 | 把语义项转换为 Unicode、ASCII、LaTeX 或其他表面形式的过程。 | 用于显示与交换给人阅读；呈现结果不参与数学内容标识。 |
| Backend binding | 后端绑定 | 把抽象语言对象映射到特定后端的类型码、词元模板和语法断言。 | 连接后端无关语义与 Metamath 等具体实现，而不改变抽象语言本身。 |
| Formation assertion | 语法形成断言 | 在后端中证明某个词元序列形成合法表达式的断言。 | 它服务于后端良构性，不是逻辑公理或推理规则。 |
| Free variable / Bound variable | 自由变量 / 约束变量 | 自由变量的出现不受当前绑定算子支配；约束变量的出现位于某个绑定作用域内。 | 用于代入、DV 检查、捕获检测和 α-等价判断。 |
| Capture-avoiding substitution | 避免变量捕获的代入 | 以项替换变量，同时通过改名等方式避免原本自由的变量被意外绑定。 | 是含绑定语言的基本语义操作；不同于 Metamath 断言实例化中的纯结构代入时，应明确区分。 |
| Alpha-renaming | α-改名 | 在不改变绑定结构的前提下系统地更换约束变量名称。 | 用于避免捕获并定义忽略约束变量拼写差异的等价关系。 |
| Backend-neutral | 后端无关 | 对象的语义不依赖某个具体证明后端、词元布局或运行时符号。 | 使同一语言、理论和证明能够被多个验证器与后端复用。 |

## 7. 第三层：判断、演算、逻辑与理论

本层描述可以对表达式作出什么判断，以及这些判断如何被公理、规则和定理推出。

| 英文术语／代码名 | 推荐中文 | 含义或定义 | 在体系中的作用 |
| --- | --- | --- | --- |
| Judgment | 判断 | 形式系统对一个或多个项作出的结构化断定，例如“公式 φ 可证”。 | 把对象语言表达式与元层面的可证性、类型性等断定分开。 |
| Judgment kind | 判断种类 | 规定一种判断的名称、参数个数及各参数类别。 | 为演算系统提供有限、可检查的判断词汇。 |
| Calculus | 演算系统 | 由判断种类和原始推理规则组成的推演体系。 | 规定判断如何从已有判断推出；与对象语言和具体理论公理相区分。 |
| Primitive inference rule | 原始推理规则 | 被演算系统直接接受、无需再由系统内部证明的推理规则。 | 构成演算的可信基础；已证明的派生规则仍应作为定理使用。 |
| Logic | 逻辑系统 | 形式语言、演算系统和逻辑公理的组合。 | 规定一类推理关系，可被多个具体数学理论复用。 |
| Theory | 理论 | 在某个逻辑之上加入领域语言、定义、非逻辑公理和定理的有组织系统。 | 作为证明构造、验证、搜索和交换的主要语义环境。 |
| Theory interface | 理论接口 | 理论向消费者公开的语言、演算、断言接口、导入要求及相关内容摘要。 | 允许其他理论和证明在不依赖具体构建过程的情况下精确引用该理论。 |
| Verification environment lock (`VerificationEnvironmentLock`) | 验证环境锁定清单 | 记录验证某份证明所需的精确语言、演算、断言接口、导入、断言应用许可集、信任策略和验证协议版本的只读清单。 | 固定完整验证环境，防止同名对象、依赖或政策漂移改变验证结论；它只记录内容与政策要求，不自动提供依赖内容，也不表示验证已经成功。它是可嵌入档案的值对象，不要求成为独立文件，也不是运行时互斥锁。 |
| Axiom | 公理 | 在给定理论或逻辑中被直接接受、没有证明前提的断言。 | 构成理论的显式假设基础。 |
| Definition | 定义 | 以定义类别登记的具名断言，用来引入或约定表达方式。 | 与公理和定理分类不同；仅标记为定义并不能自动证明其为保守扩张。 |
| Theorem | 定理 | 具有公开断言接口并由一个证明实现支持的已命名结论。 | 可作为后续证明的依赖；其接口与证明体应分别标识。 |
| Assertion | 断言 | 公理、定义、原始推理规则或已证定理在统一应用接口中的总称。 | 使证明步骤能够统一地引用和应用不同来源的推理依据。 |
| Assertion signature | 断言签名 | 断言的公开接口，包括模式变量、有序前提、结论和强制变量互异条件。 | 是验证、构造和搜索共同使用的定理级调用契约。 |
| Premise / Conclusion | 前提 / 结论 | 前提是应用断言时必须已有的判断；结论是成功应用后得到的判断。 | 确定断言应用的输入与输出。 |
| Schema variable | 模式变量 | 归属于某个断言、在应用时由具体项实例化的变量。 | 表达可复用的公理、规则和定理模式；其所有者属于变量标识的一部分。 |
| Distinct-variable condition | 变量互异条件 | 要求两个模式变量的代入结果所含变量满足指定互异关系的应用条件。 | 承载 Metamath `$d` 语义，防止不合法的变量重合。 |
| Assertion catalog | 断言目录 | 按稳定标识符收录可解析断言接口的只读集合。 | 为证明构造和验证提供确定的断言查找空间。 |
| Assertion profile (`AssertionProfile`) | 断言应用许可集（简称“断言许可集”） | 从断言目录中选出的、在特定证明构造与验证环境中允许被证明步骤应用的具名断言集合。 | 证明写作、证明搜索和语义重放在应用断言前均应检查该许可集。它限制可用推理能力，但不是用户访问权限，也不能使缺少可验证实现的定理获得可信性。 |
| Conservative extension | 保守扩张 | 扩展理论但不增加原语言中可证明结论的扩张。 | 用于评价定义或语言扩展是否改变既有理论的证明能力。 |

## 8. 第四层：证明写作与证明构造

本层描述从目标和已有前提出发形成完整证明的过程。普通线性写作与交互式、搜索式构造应共享最终合法性标准，但不必共享同一种状态表示。

| 英文术语／代码名 | 推荐中文 | 含义或定义 | 在体系中的作用 |
| --- | --- | --- | --- |
| Proof author | 证明作者 | 从事证明写作的人或主体。 | 与软件组件 `ProofAuthor` 严格区分；普通 `author` 仍按上下文译为“作者”。 |
| Proof authoring | 证明写作 | 证明作者以面向数学动作的接口书写证明步骤的活动。 | 强调用户体验和代码表达；通常由 `ProofAuthor` 提供简化入口。 |
| Proof construction | 证明构造 | 通过应用断言、求解约束和关闭目标来建立证明对象的计算过程。 | 涵盖线性写作、交互式证明和自动搜索；中文统一使用“构造”，不使用“建构”。 |
| Proof-authoring interface (`ProofAuthor`) | 证明编写器 | 服务于完整、前向、线性证明写作的简化软件接口。 | 绑定理论环境，并通过 `use()` 和 `qed()` 隐藏底层草稿、检查和完成过程；它不是证明作者本人。 |
| Proof draft (`ProofDraft`) | 证明草稿 | 尚未最终完成的证明记录。当前实现中的 `ProofDraft` 实际只容纳已经具体化并立即检查过的步骤。 | 术语上应与真正含目标、空缺和元变量的证明状态区分；当前类更接近“已检查证明前缀”。 |
| Checked proof prefix | 已检查证明前缀 | 由有序前提和已经通过局部检查的具体证明步骤组成的前缀。 | 更准确地描述当前 `ProofDraft` 的语义，并可作为其未来内部名称。 |
| Proof state (`ProofState`) | 证明状态 | 包含待证目标、局部步骤、元变量、约束和精确理论环境的不可变构造快照。 | 作为交互式证明和搜索的公共数学状态；搜索评分与搜索树元数据不属于其中。 |
| Goal | 待证目标 | 证明状态中尚未关闭的判断。 | 为精化动作提供明确对象；公共接口宜通过稳定的 `GoalId` 引用。 |
| Hole | 证明空缺 | 证明结构中尚未填入完整推导的占位位置。 | 只属于构造层，不得进入最终完整证明或验证器使用的核心 `Term`。 |
| Metavariable | 元变量 | 构造过程中代表尚未确定之项的内部变量。 | 承载未完全确定的代入，并由合一和约束求解逐步确定。 |
| Constraint | 约束 | 证明构造中必须满足的条件，例如项相等、类别一致或变量互异。 | 允许反向应用断言时暂时保留未决信息，完成证明前必须全部解决。 |
| Elaboration | 详化 | 把作者层或源码层中带有简写、作用域、隐含信息或部分指定的对象，经过解析、补全、消歧和约束生成，转换为更显式的核心表示的过程。 | 详化过程中可以产生元变量和未决约束，也可以包含展开；它不同于单纯的展开、对证明目标的精化、完成检查和语义验证。 |
| Refinement | 证明精化 | 针对一个待证目标应用断言或构造动作，并产生更具体的新状态及可能的子目标。 | 是交互式证明和搜索的基本状态转移；对应 `ProofState.refine()`。 |
| Forward / Backward construction | 前向构造 / 反向构造 | 前向构造从已有前提出发产生新结论；反向构造从目标出发分解出子目标。 | 分别对应 `ProofAuthor.use()` 的主要路径与 `ProofState.refine()` 的主要路径。 |
| Proof step / Step reference | 证明步骤 / 步骤引用 | 证明步骤是一次具体断言应用或假设出现；步骤引用是对该出现位置的值式引用。 | 在证明内部连接前提与结论；引用应为证明局部或状态演化链局部，不必成为全局对象。 |
| State transition | 状态转移 | 从一个不可变证明状态和一个构造请求确定性地产生新状态或结构化失败的过程。 | 为搜索器提供稳定、可批量化的核心操作。 |
| Branch | 分支 | 从同一不可变状态执行不同精化动作而得到的多个后继状态。 | 表达搜索空间；保留原状态即可实现撤销，无需在核心状态中维护显式 undo。 |
| Snapshot / Lineage | 状态快照 / 演化链 | 快照是某一时刻的完整不可变状态；演化链是由连续状态转移形成的祖先—后继关系。 | 限定 `GoalId`、`MetaId` 和步骤引用的稳定范围，并支持状态摘要。 |
| Unification | 合一 | 求解使两个项结构一致的代入。 | 用于断言应用、目标匹配和元变量求解。 |
| Instantiation | 实例化 | 按照一份完整代入，把断言中的模式变量替换为具体项。 | 从断言模式计算具体前提和结论；验证器必须能够独立重算。 |
| Finalization | 完成检查 | 在所有目标和约束关闭后，检查根结论、可达性和其他完整性条件，并生成完整证明。 | 构造层通向完整证明层的唯一出口；对应 `qed()` 或 `finish()`。 |

## 9. 第五层：完整证明、验证与信任

本层区分“对象已经完整形成”与“对象已在某个精确理论环境下通过验证”。内容摘要不构成验证结论。

| 英文术语／代码名 | 推荐中文 | 含义或定义 | 在体系中的作用 |
| --- | --- | --- | --- |
| Complete proof | 完整证明 | 不含目标、空缺、元变量或未决约束，且所有步骤均为具体断言应用的证明对象。 | 作为验证、交换、后端转换和分析的共同核心对象。 |
| Elaborated proof (`ElaboratedProof`) | 完整证明对象（现有代码名） | 当前 API 中表示经过详化和完成检查后形成的证明类。 | 中文正文宜直接称“完整证明”，避免把类名机械译成生硬的新术语；未来可演进为公开 `Proof`。 |
| Proof DAG | 证明有向无环图（证明图） | 以假设和断言应用为节点、以前提依赖为边的有向无环结构。 | 保存证明的共享依赖关系，并支持可达性、依赖和重放分析。 |
| Root | 根结论 | 完整证明最终指定的结论节点。 | 确定证明所实现的定理结论，并界定哪些步骤属于有效证明闭包。 |
| Direct dependency / Dependency closure | 直接依赖 / 依赖闭包 | 直接依赖是证明步骤明确引用的断言集合；依赖闭包进一步递归包含这些定理的依赖。 | 区分局部重放所需接口与整套理论验证、发布和审计所需的传递依赖。 |
| Structural validation | 结构检查 | 检查证明对象内部形状是否合法，例如步骤编号、引用方向、根结论和可达性。 | 只能说明对象结构自洽，不能证明每次断言应用在理论中有效。 |
| Semantic verification | 语义验证 | 在精确理论环境下重新解析并应用每一步断言，重算代入、结论、DV 条件和依赖。 | 给出证明是否有效的权威判定；对应 `Theory.verify()` 或 `verify_proof()`。 |
| Assertion-application kernel | 断言应用内核 | 对一次具体断言应用执行合一、完整代入、结论计算、类别检查和 DV 检查的共同核心。 | 必须被证明写作、语义重放和最终完成检查共同复用，以保持唯一合法性标准。 |
| Replay | 语义重放 | 根据记录的断言引用、前提位置和代入，逐步重新执行并核对证明。 | 把证明对象从“被声明的数据”转化为“经独立重算确认的数据”。 |
| Replay context | 重放上下文 | 重放证明时必须保留的环境信息，例如活动 DV 关系和精确断言接口要求。 | 确保同一证明步骤在交换、加载或后端转换时仍按原语义解释。 |
| Verification report | 验证报告 | 验证器返回的结构化结果，至少包含成功状态、稳定错误码、位置、期望值、实际值及相关证据。 | 是普通 API 表达验证结论和审计信息的主要对象。 |
| Diagnostic | 诊断信息 | 对构造或验证失败的机器可读分类及上下文说明。 | 供搜索、批处理、修复、训练数据和用户界面稳定消费；不能只依赖异常文本。 |
| Evidence / Witness | 证据 / 见证 | 验证器重算得到的支持性数据，例如满足 DV 条件的变量对或失败冲突位置。 | 帮助审计和诊断，但不应作为未经核对的第二份权威输入。 |
| Trust policy | 信任策略 | 规定哪些原始声明、外部依赖或特殊免证对象可以作为验证基础的明确政策。 | 使证明的数学实现与采用何种信任边界分离。 |
| Trust root | 信任根 | 信任策略明确批准、无需由当前理论进一步证明的基础声明。 | 构成验证最终落脚的显式可信基础。 |
| Oracle | 免证断言（代码中可称 `oracle`） | 由高级信任策略明确允许、但没有可验证实现的外部断言。 | 必须进入验证报告和信任依赖，不得因出现在目录或许可集中而隐式获得可信性。 |
| Trust closure | 信任依赖闭包 | 一份证明经传递依赖最终涉及的全部信任根、免证断言和其他显式假设。 | 用于说明“这份证明最终相信了什么”；正文可解释为“最终信任基础”。 |
| Verification certificate | 验证证书 | 可独立保存或传递、证明某一实现已在特定验证环境锁定清单下通过验证的证据对象。 | 不同于内容摘要和普通验证报告；其格式与安全语义必须另行规范。 |
| Independent verifier | 独立验证器 | 不依赖生产者的可执行代码、由独立实现重新检查证明的验证器。 | 降低共同实现缺陷带来的风险，并作为交换格式冻结前的重要一致性检验。 |

## 10. 第六层：标识、同一性与摘要

本层是当前文档最需要严格区分的部分。`identifier`、`identity`、`digest` 与“已经验证”不是同一概念；英文 `identity` 不应一律译为“身份”。

| 英文术语／代码名 | 推荐中文 | 含义或定义 | 在体系中的作用 |
| --- | --- | --- | --- |
| Identifier | 标识符 | 用于引用一个对象的稳定名称或结构化键。 | 回答“如何指到它”，不单独回答“它的内容是什么”或“它是否有效”。 |
| Nominal identifier | 名称标识符 | 由命名空间和局部名称构成、表达对象声明名称的稳定标识符。 | 允许同一概念在版本间保持可读名称，同时通过内容摘要检查兼容性；不译为“名义身份”。 |
| Object identity | 对象同一性 | 两个引用是否指向同一个运行时对象的关系。 | 可用于某些进程内所有权检查，但不能作为跨进程、跨序列化的数学标识。 |
| Semantic identity | 语义同一性 | 按照明确规范判定两个语义对象是否代表同一内容的关系。 | 必须说明采用何种规范化和等价关系；不能仅凭名称或 Python 对象地址判断。 |
| Content equality | 内容一致 | 两个对象的规范表示完全相同。 | 通常由相同版本、相同摘要域下的内容摘要进行快速判断；它不等于数学等价。 |
| Canonical form | 规范形式 | 一个规范明确规定、对同一内容产生唯一表示的形式。 | 为确定性序列化、摘要和跨实现一致性提供基础。 |
| Canonical projection | 规范表示映射 | 从内存对象提取进入规范表示的权威字段和顺序的映射。 | 决定哪些字段参与内容摘要，哪些只是缓存、显示或伴随数据；中文正文不宜只写含糊的“投影”。 |
| Digest | 摘要 | 对带版本、带域的规范字节表示计算所得的固定长度哈希值。 | 用于内容一致性检查、缓存和内容寻址；摘要本身不是有效性证书。 |
| Semantic digest | 语义摘要 | 只覆盖对象语义内容、不包括显示记法、源码位置或溯源信息的摘要。 | 用于判断语义接口或对象内容是否一致；旧字段名不得暗示对象已经验证。 |
| Interface digest | 接口摘要 | 对语言、断言或理论公开接口内容计算的摘要。 | 固定消费者所依赖的契约；定理证明体变化不应改变定理接口摘要。 |
| Implementation digest | 实现摘要 | 对某个接口的具体实现内容计算的摘要，例如定理接口、证明图、重放上下文和精确依赖要求。 | 标识一份具体证明实现，同时与验证策略和验证结果分离。 |
| Verification digest | 验证摘要 | 对实现摘要和验证环境锁定摘要共同计算的结果标识；后者已经覆盖许可集、信任策略和验证协议版本。 | 作为验证结果缓存键或报告标识；它不代替实际验证过程、数字签名或证书。 |
| Verification environment lock digest | 验证环境锁定摘要 | 对验证环境锁定清单规范内容计算的摘要。 | 精确标识完整验证环境要求，便于缓存、审计和交换；对应字段可命名为 `verification_environment_lock_digest`。 |
| Domain separation | 摘要域分离 | 为不同对象种类和协议版本使用不同的摘要前缀或命名域。 | 防止同一字节串在不同语义对象中被误认为同一种内容。 |
| Content-addressed reference | 内容寻址引用 | 以内容摘要而不是可变路径或仅有名称来定位对象的引用。 | 使精简档案能够精确取得依赖，并检测解析到的内容是否匹配。 |
| Cache key | 缓存键 | 用于定位可复用计算结果的稳定键。 | 可以由实现摘要或验证摘要派生，但缓存命中不能绕过必要的版本和信任条件检查。 |

## 11. 第七层：交换、序列化与溯源

本层规定证明如何以纯数据形式保存、传递和重新验证。英文 `artifact` 必须按上下文翻译，不设无条件适用的单一中文对应词。交换与持久化语境使用“档案”，构建与生成流程使用“产物”；“档案”不表示对象必须是文件、压缩包或传统 archive。

| 英文语境 | 推荐中文 | 使用条件 |
| --- | --- | --- |
| `artifact`（无修饰） | 避免单独使用 | 应补出对象种类或生命周期，不能仅凭该词判断它是交换对象还是构建输出。 |
| `exchange artifact` / persistent artifact | 交换档案 / 档案 | 指带版本、可持久保存和传递、能由其他进程或实现严格解码的纯数据对象。 |
| `proof artifact` / `theory artifact` | 证明档案 / 理论档案 | 指分别承载证明内容或理论接口、实现与依赖信息的交换档案。 |
| self-contained / thin artifact | 自包含档案 / 轻量档案 | 根据验证依赖是随档案嵌入还是通过内容寻址引用外置来区分。 |
| `build artifact` | 构建产物 | 指编译、后端转换或打包产生的可再生成输出，例如 `.mm`、源码映射或构建报告。 |
| `generated artifact` | 生成产物 | 泛指生成流程的输出；如果该对象已经满足证明档案或理论档案的交换契约，应改用相应的“档案”名称。 |
| artifact envelope / artifact codec | 档案封装 / 档案编解码规范（器） | 只用于交换档案的外层结构和编解码边界。 |

| 英文术语／代码名 | 推荐中文 | 含义或定义 | 在体系中的作用 |
| --- | --- | --- | --- |
| Artifact | 按语境使用“档案”或“产物” | 软件工程中对人工产生或开发流程生成之可交付对象的宽泛称呼，其确切含义由生命周期和使用边界决定。 | 中文正文不得机械翻译为“制品”或“工件”，也应避免无修饰地单独使用；交换对象称“档案”，构建输出称“产物”。 |
| Proof artifact / Theory artifact | 证明档案 / 理论档案 | 分别保存一份证明或一套理论接口、实现和依赖信息的版本化数据对象。 | 支持跨进程交换、长期存档和独立验证。 |
| Serialization | 序列化 | 把语义对象编码为可存储或传输的字节表示。 | 是交换边界的一部分；不得依赖 Python `repr`、pickle 或执行生产者代码。 |
| Codec | 编解码规范 / 编解码器 | 规定对象如何编码、解码以及如何处理版本、字段和错误的规范及实现。 | 确保不同实现对同一档案得到相同规范字节和相同接受或拒绝结果。 |
| Schema | 数据模式 | 规定序列化对象允许出现的字段、类型、结构和版本。 | 约束档案的外部形状；不要与断言中的模式变量混淆。 |
| Wire format / Wire schema | 序列化格式 / 序列化格式规范 | 跨进程或跨实现传递时采用的精确字节与数据结构约定。 | 中文正文不使用“线格式”“线上模式”等直译。 |
| Envelope / Payload | 外层封装 / 主体数据 | 外层封装承载版本、类型和附加区段；主体数据是被封装的证明或理论内容。 | 把文件级元数据与核心数学对象分开。 |
| Strict decoder | 严格解码器 | 对未知版本、缺失或多余字段、重复键、畸形标识符及超限输入明确拒绝的解码器。 | 构成接收不可信输入时的第一道安全边界。 |
| Unchecked packet | 未核验原始数据 | 严格解码后、尚未经过语义重放和依赖验证的短生命周期内部对象。 | 只能在解码器内部流转，不能冒充公开完整证明。 |
| Self-contained / Thin artifact | 自包含档案 / 轻量档案 | 自包含档案嵌入验证所需的完整依赖内容；轻量档案只记录精确的内容寻址引用。 | 对应离线可验证与依赖外置两种交换策略；轻量档案在依赖缺失或摘要不符时必须拒绝。 |
| Resolver | 依赖解析器 | 根据稳定标识符和内容摘要取得精确接口或实现的组件。 | 为轻量档案和理论导入提供内容；解析结果必须再次核对摘要。 |
| Canonical JSON | 规范化 JSON | 对对象字段、数组顺序、数值和字符串编码作出唯一规定的 JSON 表示。 | 可作为第一版人可读交换编码，并为跨实现摘要一致性提供基础。 |
| Round trip | 编解码往返 | 对象经过编码、解码并再次编码后保持语义不变，并在规范要求下保持字节完全一致。 | 检验编解码规范的确定性与无损性。 |
| Golden vectors | 标准测试向量 | 一组固定的应接受和应拒绝输入及其预期规范字节、摘要或错误码。 | 供独立实现复现格式行为，是冻结交换规范前的发布门槛。 |
| Sidecar | 伴随数据 | 通过主体摘要与证明或理论关联、但不进入核心语义内容的附加数据。 | 承载源码映射、叙述、搜索评分、计时和溯源信息；中文正文不使用“边车”。 |
| Provenance | 溯源信息 | 记录对象的作者、来源、生成过程、工具版本和构建链条的信息。 | 支持审计、引用和复现，但默认不改变证明实现摘要。 |
| Source map / Build record | 源码映射 / 构建记录 | 源码映射连接语义对象与作者源位置；构建记录保存构建环境和过程信息。 | 帮助诊断与复现，通常作为伴随数据保存。 |
| Digital signature | 数字签名 | 由密钥对某份确定字节内容作出的密码学签名。 | 证明签发者与内容之间的关系；不同于断言签名、内容摘要和验证证书。 |
| Fail closed | 出错即拒绝 | 遇到未知、缺失、冲突、解析失败或资源超限时，默认不接受输入。 | 是加载不可信档案和解析依赖时的安全原则；不使用“失败关闭”等直译。 |
| Resource limit | 资源限制 | 对总字节数、项深度、步骤数、字符串长度和集合大小等设定的硬上限。 | 防止畸形或恶意档案造成内存、CPU 或递归深度耗尽。 |

### 11.1 生成源码表面

| 英文术语／代码名 | 推荐中文 | 含义或定义 | 在体系中的作用 |
| --- | --- | --- | --- |
| Generated source surface | 生成源码表面 | 生成的 Python 源代码所呈现的公共写作形态；它是具体语法，不是语义事实源。 | 为 IDE 跳转、补全、审查和手写扩展提供稳定表面，同时保持项与断言接口为同一性依据。 |
| Lazy elaboration | 惰性详化 | 证明体登记后，延迟到首次访问实现、显式验证或构建发射时才执行的详化策略。 | 避免包导入时执行证明；首次详化结果必须缓存，导入本身不得触发详化。 |
| Step-result comment | 步骤结论注释 | 生成器由已核验步骤结果渲染的行尾注释。 | 作为派生、非语义的可读性信息；再生成时重算，不解析回语义对象，也不进入摘要。 |
| Header/local import rule | 头部/局部导入规则 | 文件头只导入框架公共物，跨模块断言引用只在证明函数体内局部导入的确定性规则。 | 使模块导入与惰性详化兼容，并让 Python import 图显式表达证明依赖。 |
| Assertion handle | 断言句柄 | 断言声明返回的模块级绑定对象，承载断言签名、证明体登记入口和惰性实现属性。 | 是生成证明体引用断言的权威通道；字符串 label 索引仅作为派生视图。 |
| Emission binding | 发射绑定 | 由 profile 与源数据库机械派生、用于声明级 Metamath 发射的版本化数据。 | 固化常量、变量、formation、混排顺序和假设标签政策；不承载证明内容。 |
| Frame-equivalence gate | 帧等价门 | 独立解析两份 Metamath 输出后，比较断言序列、表达式、mandatory 假设和 distinct 约束的验收门。 | 忽略按位归一化后的假设 label 文本与证明 token 偶然差异，同时保持语义比较出错即拒绝。 |
| Derived syntax theorem | 派生语法定理 | 结果 typecode 属于语言 term typecode、且不属于任何 judgment typecode 的源 `$p` 断言。 | 表示可由 formation 声明组合重放的具体语法便利；比较器只能依据 profile 机械判类。 |

## 12. 第八层：后端执行与证明搜索

执行表示是完整证明的派生表示；搜索算法是证明状态之上的外部控制层。两者都不应反向污染核心数学对象。

| 英文术语／代码名 | 推荐中文 | 含义或定义 | 在体系中的作用 |
| --- | --- | --- | --- |
| Backend | 后端 | 消费后端无关语义对象并产生特定证明系统、文件或执行形式的实现。 | 例如 Metamath 输出与验证路径；后端细节不应进入抽象语言和证明内容标识。 |
| Lowering | 后端转换 | 把较高层、后端无关的对象转换为更具体、可执行或可输出的后端表示。 | 中文正文使用“转换为后端表示”，不机械翻译为“降低”或“降级”。 |
| Execution representation | 执行表示 | 断言引用已解析、步骤线性化且不再包含推断任务的派生表示。 | 供高吞吐验证、Metamath 输出或未来虚拟机消费；不应成为普通作者必须操作的公共对象。 |
| Replay plan | 重放序列 | 由完整证明导出的、按确定顺序执行语义重放或后端转换的步骤序列。 | 当前 `SemanticReplayPlan` 可作为内部对象；正文不宜把它误写成验证本身。 |
| Search engine | 证明搜索器 | 在 `ProofState` 上选择候选动作、维护分支并决定探索顺序的外部组件。 | 复用核心状态转移和最终验证标准，但搜索策略不进入证明状态。 |
| Search frontier | 搜索前沿 | 尚待展开的一组搜索节点或证明状态。 | 属于搜索器的调度数据，不属于数学证明状态或最终证明。 |
| Candidate action | 候选动作 | 搜索器拟在某个目标上尝试的断言应用、代入或其他精化请求。 | 作为状态转移的输入，可由规则索引、模型或启发式方法生成。 |
| Scoring / Ranking | 评分 / 排序 | 对候选动作或搜索节点赋值并决定优先级的外部策略。 | 模型分数、束搜索分数和访问次数不得进入证明的语义摘要。 |
| Batch transition | 批量状态转移 | 对同一或多个证明状态一次处理多个候选动作的接口。 | 用于提高搜索吞吐量；逐项结果必须与标量状态转移一致。 |
| State deduplication | 状态去重 | 识别并合并被认为等价的搜索状态。 | 首版快照摘要只保证相同规范字节得到相同摘要，不自动承诺数学状态等价。 |
| Alpha-equivalence / Proof equivalence | α-等价 / 证明等价 | α-等价忽略约束变量改名；证明等价是更强、必须另行定义的证明关系。 | 可服务高级去重与分析，但在有真实收益证据前不应进入 v1 内容标识。 |
| Normalization | 规范化 | 按照确定规则把对象转换为选定规范形式的过程。 | 可服务比较、压缩和缓存；必须明确其保持的语义和版本。 |
| Proof repair | 证明修复 | 在依赖、接口或局部步骤变化后，寻找使证明重新有效的修改。 | 建立在结构化诊断、证明图和搜索能力之上，不属于最小验证内核。 |
| Semantic diff | 语义差异 | 比较两个证明或理论对象在规范语义内容上的变化。 | 用于审查、迁移和修复；与源码文本差异或格式变化相区分。 |
| Dependency minimization | 依赖最小化 | 在保持证明有效的前提下删除不必要的断言或理论依赖。 | 用于审计、发布、切片和生成更小的自包含档案。 |

## 13. 第九层：知识组织与发布

本层规定知识库划分与发布相关的词汇（裁决来源：Project 026，
2026-07-19）。

| 英文术语／代码名 | 推荐中文 | 含义或定义 | 在体系中的作用 |
| --- | --- | --- | --- |
| Release package | 发布包 | 知识库的发布与安装单元，整体版本化；可包含多个数学领域。 | 构建、版本、分发以此为单位；transpiler 生成的顶层分发单元。其容纳多领域的能力**尊重数学的知识传统**：缠绕的学科共同发布，无须为发布被拆散。 |
| Mathematical domain | 数学领域 | 发布包的一级子包，对应一个数学学科（含桥领域）的命名空间与社区边界。 | 同一发布包内领域间依赖必须构成 DAG（026 P7），该无环要求**尊重工程实践**（构建、lazy 加载、版本化）。领域不是依赖层：其具体分层顺序是当前语料的快照，随知识生长变化。 |
| Bridge domain | 桥领域 | 内容本质上耦合两个以上核心领域的数学领域，沿用数学传统命名（如算术组合学、解析数论）。 | 吸收跨领域缠绕，使核心领域保持窄边界；是领域 DAG 在知识缠绕下仍可维持的机制。 |
| Module | 模块 | 领域内部的最小组织单元（文件或子包）：路径与名字由分类声明，依赖由 import 声明。 | 依赖硬约束的粒度：模块 import 图必须无环且完备（026 P3/P4）；语句归属跟随证明依赖。 |
| Prelude | 前导包 | 发布包内全局隐式可见的基础层。**当前维持极小 pre-logic 状态**；若扩展，边界判据为**通用理论构造能力**（候选边界到集合/类基础、关系与函数为止，贴近 set.mm 原生分层），不承载具体数学领域的实质理论；自然数（含 ω）、有限性、归纳与有限递归不入前导包。 | 是否/何时扩展是 027 RFC 的首项开放问题；判定框架与否定性裁决已冻结。语义基础归前导包，书写经济性归 Python 层。 |
| Capability slice | 能力簇 | 一个构造连同其形成、相等替换、引入消去与递归归纳规则的最小可用闭包。 | 前导包与领域包之间的**迁移单位**（027 §3）：迁移以能力簇为整体，不以单个 label 或频率排名。 |
| Profile | 聚合包 | 只含稳定聚合依赖、不拥有底层定义的发布包（如 learning profile、program profile）。 | 为应用场景提供开箱即用入口而不破坏理论边界；应用需求经聚合包组装，不得反向压迫前导包（027 §1/§5）。 |

## 14. 应避免的生硬表达

| 不推荐表达 | 推荐改写 | 说明 |
| --- | --- | --- |
| proof protocol | 证明对象规范；特指序列化时写“证明交换格式” | 避免把 protocol 当作无差别总称。 |
| content identity | 内容一致性／内容标识 | 根据语境说明是等价关系还是摘要标识。 |
| nominal identity / nominal ID | 名称标识符 | 不使用“名义身份”。 |
| mental model budget | 公共概念限额；或“控制用户必须理解的概念数量” | 用直接汉语陈述设计目标。 |
| acceptance boundary | 统一合法性判定 | 避免“接受边界”式直译。 |
| execution projection | 执行表示 | 比“执行投影”更直接。 |
| happy path | 默认流程／常规流程 | 不在规范正文中保留口语化英语。 |
| fail closed | 出错即拒绝 | 不使用“失败关闭”。 |
| sidecar | 伴随数据 | 不使用“边车”。 |
| thin artifact | 轻量档案 | 不使用“薄制品”。 |
| artifact identity | 档案内容摘要／档案内容一致性 | 必须说明究竟指摘要还是等价关系。 |
| lowering | 转换为后端表示／后端转换 | 不使用“降低”“降级”。 |
| progressive disclosure | 按需呈现复杂性 | 用完整汉语表达，而非固定成抽象名词。 |
| low ceremony | 使用负担低／调用简洁 | 避免直译“低仪式感”。 |

## 15. 文档维护规则

1. 每个新公共类型进入设计文档前，应先检查本术语规范中是否已有对应概念。
2. 新增术语时至少给出：英文名称、推荐中文、定义、在体系中的作用。
3. 一个术语若改变含义，应更新本文件的版本，并列出受影响的 API、字段和文档。
4. 代码名与自然语言名称可以不同，但映射必须明确且保持稳定。
5. 争议术语在冻结前标记为“暂定”；冻结后如需修改，应视为文档与 API 的兼容性变更。
6. 本文件按概念层次组织；后续可从同一术语数据生成英文字母索引和中文索引。
