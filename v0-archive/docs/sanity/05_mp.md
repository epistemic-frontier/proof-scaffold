# M0.2 / Sanity Step 05 — MP (Modus Ponens) Design Note

## Purpose (Engineering)

Step 05 exists to validate the first “real” linker-relevant invariant:

> A theorem’s proof token list references `$a/$p` labels, which forms a concrete
> dependency edge (`uses_assertions(T)`), and rule application semantics depend
> on ordered essential hypotheses (`$e`).

This is the smallest sanity step that:
- uses an assertion label as an executable rule,
- relies on `$e` hypotheses as ordered stack inputs,
- produces distinct failure modes that are predictable and testable.

## Fixtures

We provide three fixtures under `fixtures/sanity/`:

1) `05_mp_happy.mm`
   - Must be accepted by verifier.
   - Proof token sequence: `h1 h2 ax-mp`.

2) `05_mp_missing_hyp.mm`
   - Must be rejected by verifier.
   - Proof token sequence: `h1 ax-mp`.
   - Failure type: missing essential hypothesis (stack underflow / mismatch).

3) `05_mp_bad_proof_tokens.mm`
   - Must be rejected by verifier.
   - Proof token sequence: `h2 h1 ax-mp`.
   - Failure type: hypothesis order mismatch.

## Acceptance Criteria

The sanity runner `tools/sanity/check_05_mp.py` must:

- run verifier on all three fixtures
- assert:
  - happy case: return code == 0
  - failure cases: return code != 0
- print a short, structured report indicating which case failed and why
  (at least surface the verifier stderr/stdout snippet)

## Notes on Minimality

This step intentionally avoids:
- `$d` constraints
- multi-module linkage
- token relocation

It focuses purely on:
- `$e` semantics,
- proof token stack discipline,
- rule invocation via labels.

Later steps (06–07) will connect these mechanics to scope frames and multi-unit linkage.
