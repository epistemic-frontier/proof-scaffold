# ProofScaffold — Agent Guide for M1.1

**Milestone: Linker v0**

## 0. Milestone Definition（先统一目标）

**M1.1 = 第一个真正可用的 Linker（Linker v0）**

完成 M1.1 意味着系统具备：

* 多 ProofUnit、跨模块的确定性链接
* token 级 relocation（不依赖 generator 的字符串命名）
* 保守、可诊断的 scope 规划
* 失败可以定位回 generator 调用点

**明确非目标（M1.1 不做）：**

* 不做 `$d` 推导（仅 pass-through）
* 不做 scope 合并或优化
* 不做 proof compression 或性能优化
* 不支持 stringly-typed proof body（除非显式 COMPAT）

---

## 1. 输入与约束（硬规则）

### 1.1 Linker 的唯一输入

* **LIR 是唯一真实输入**
* 所有：

  * math string
  * proof tokens
* **必须是 `SymbolRef[]`**
* 默认禁止 raw string token（COMPAT 必须显式开启）

> 违反即 fail fast（Stage 1）

---

## 2. 必须实现的 Linker Pipeline（最小闭环）

仅实现 **baseline 版本**，不做优化。

### Stage 1 — Symbol Resolution & Early Lint

**必须做到：**

* 构建全局 Symbol Table
  `(origin, local_name, kind) → SymbolId`
* 解析所有 token 为 `SymbolRef`
* 检查并报错：

  * 跨 ProofUnit 使用 `$f / $e`
  * 引用未 export 的 `$a / $p`
  * 非 COMPAT 模式下出现 raw string token

---

### Stage 4 — Dependency Closure & Topo Sort

**必须做到：**

* 从 proof tokens 中提取 `uses_assertions`
* 允许 generator 提供 `requires` 作为 **hint**
* Linker 必须计算真实闭包
* 检测并拒绝依赖环

---

### Stage 5 — Scope Planning（保守版）

**规则（不可讨论）：**

* 每个 ProofUnit → **一个独立 `${ ... $}`**
* Unit-local `$f / $e / $d` 在 scope 内声明
* Exported `$a / $p` 在该 scope 内定义
* 不合并 scope，不共享上下文

---

### Stage 6 — Token-level Relocation

**必须覆盖所有 token：**

* labels
* math strings
* proof tokens

**要求：**

* relocation 由 Linker 完成
* generator 不负责命名唯一性
* 输出命名必须：

  * 确定性
  * 可重复构建
  * 冲突可处理（hash suffix）

---

### Stage 7 — Two-phase Emission

**输出顺序固定：**

1. **Global Header**

   * 所有 `$c`
   * 所有 `$v`
2. **Body**

   * ScopeFrames
   * `$d / $f / $e / $a / $p`

---

## 3. Diagnostics（M1.1 的关键价值）

### 3.1 Origin-first 原则（必须）

所有 IR 节点必须携带：

* `origin = (module, file, line)`

包括：

* SymbolDef
* Statement
* ProofUnit
* （如有）HIR Apply step

### 3.2 错误报告最低标准

**任何 linker error 必须能回答：**

> “这是哪个 generator 调用点产生的？”

实现方式不限，但错误信息中必须包含 origin 链。

> M1.1 不要求完整 SourceMap，只要求 **可追责**。

---

## 4. `$d` 策略（严格限制）

* **仅 Mode A（pass-through）**
* Linker 只负责：

  * 放置 generator 提供的 `$d`
  * 确保 `$d` 在 assertion 定义点 active
* verifier 报 `$d` 错误 → 回 generator 修

---

## 5. 验收标准（Definition of Done）

M1.1 **完成** 当且仅当：

1. ✅ 多 ProofUnit、跨模块示例可以 link 并通过 verifier
2. ✅ 同一输入多次构建，输出字节级或 token 级一致
3. ✅ label 名称冲突可被 relocation 正确处理
4. ✅ 故意制造错误时：

   * 错误在 Stage 1–7 中尽早失败
   * 错误信息包含 generator 的 origin 信息
5. ✅ CI 默认关闭 COMPAT（raw string token 不能“偷偷溜进来”）

---

## 6. 一句话总结（给 agent 记住）

> **M1.1 的成功标准不是“功能多”，
> 而是：Linker 成为唯一可信的结构裁判。**

# M1.1 测试完成目标（通过即验收）

## A. Sanity Tests（必须全绿，CI 常驻）

这些测试对应“最小闭环 + verifier 接受”，一旦挂了就说明系统回路断裂。

### A1. `sanity_m11_single_unit_links`

**目标**：单 ProofUnit（LIR-only）→ linker → emit → verifier ✅
**断言**：

* 生成的 `.mm` 可被 verifier 接受
* 输出包含两段结构：header（`$c/$v`）+ body（`${...$}`）

### A2. `sanity_m11_two_units_cross_module_links`

**目标**：两个 ProofUnit，跨模块 import/export，依赖闭包正确 → verifier ✅
**断言**：

* topo 顺序正确（被依赖的导出在前）
* 每个 ProofUnit 都被包在独立 `${ ... $}` 中（保守 scope 规划）

---

## B. Golden Tests（确定性与 relocation 快照）

这些测试确保“同输入同输出”，把确定性变成硬约束。

### B1. `golden_m11_deterministic_emission`

**目标**：同一 IR 输入跑两次，输出 token 序列完全一致（或字节一致）
**断言**：

* `emit(run1) == emit(run2)`（建议做 byte-identical）
* 不允许依赖 Python set/dict 的随机迭代顺序

### B2. `golden_m11_relocation_snapshot`

**目标**：固定 IR 输入下，relocation 后的符号命名稳定，并与 golden 文件一致
**断言**：

* 导出 label 的最终 emitted name 与快照一致
* proof token 中引用的 label 也被一致性改写（token-level relocation）

---

## C. Adversarial Tests（必须“早失败”，错误可定位）

这些测试确保“越早拒绝越好”，且错误信息能追溯到 generator 调用点（origin）。

### C1. `adv_m11_forbid_raw_string_tokens_default_off`

**目标**：默认模式下出现 raw string token → Stage 1 直接失败
**断言**：

* 报错发生在 symbol resolution / early lint 阶段
* 错误信息包含 origin（module + file:line）

> 可加一个对应的 `adv_m11_allow_raw_string_tokens_compat_on`：显式 COMPAT 开启时允许通过（但 CI 默认必须关）。

### C2. `adv_m11_forbid_cross_unit_hyp_leakage`

**目标**：proof tokens 引用了另一个 unit 的内部 `$f/$e` → Stage 1 失败
**断言**：

* 明确指出“跨 unit hypothesis 泄漏”
* 错误包含引用点与被引用符号的 origin

### C3. `adv_m11_forbid_non_export_label_reference`

**目标**：引用另一个模块未 export 的 `$a/$p` label → Stage 1 失败
**断言**：

* 错误说明“non-exported label”
* 包含 origin

### C4. `adv_m11_dependency_cycle_detected`

**目标**：A 依赖 B，B 依赖 A → Stage 4（closure/topo）失败
**断言**：

* 报错指出 cycle，并列出 cycle 路径（至少 A→B→A）
* 包含相关 ProofUnit 的 origin

### C5. `adv_m11_scope_unbalanced_rejected`

**目标**：IR 中 scope enter/exit 不平衡 → emission 前失败（Stage 5/7 任一处）
**断言**：

* 失败发生在 linker 内，而不是留给 verifier 才炸
* 错误定位到具体 unit/stmt 的 origin

---

## D. Structural Conformance Tests（输出结构硬约束）

这些测试把 v3 的“中端不变量”落到可自动检查的形式（即使暂不做 SourceMap 完整版）。

### D1. `struct_m11_header_hoist_only`

**目标**：所有 `$c/$v` 只能出现在 header，不得落在任何 `${...$}` 内
**断言**：

* body 中不出现 `$c` / `$v`

### D2. `struct_m11_one_unit_one_scopeframe`

**目标**：每个 ProofUnit 独立 scope frame
**断言**：

* unit 数量 == `${` 数量 == `$}` 数量
* unit 边界不跨 scope

### D3. `struct_m11_token_level_relocation_total`

**目标**：确保 relocation 覆盖所有 token 类别
**断言**：

* labels / math strings / proof tokens 中不存在未改写的“原始局部名”（可以用“局部名哨兵”设计测试数据）

---

# 最小“通过门槛”（建议写进 CI）

当且仅当以下集合全绿，允许宣告 M1.1 done：

* Sanity：A1、A2
* Golden：B1、B2
* Adversarial：C1–C5
* Structural：D1、D2、D3

这套目标与 Roadmap 的 M1.1～M1.6 的核心验收点是对齐的：LIR foundation、early lint、dependency closure、conservative ScopeFrames、token-level relocation、two-phase emission。
