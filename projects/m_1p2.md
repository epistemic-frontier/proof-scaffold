# ProofScaffold — Agent Guide for M1.2（含 M1.2a + M1.2）

> 目标：把 Linker 从“能跑”推进到“**能追责、能早拒绝、能稳定复现**”的工程状态。
> 设计依据：架构与信任边界 ；Linker Model v3（IR/合同/阶段）；Roadmap（里程碑定义与验收）；Generator 侧配合与迁移策略 。

---

## 0. Milestone Definition（先统一目标）

### 0.1 里程碑定义

**M1.2a = Traceability Infrastructure（内部基础设施）**
做到“任何一次失败都能回答：这是哪个 generator 调用点造成的？链路上经历了哪些 pass/上下文？”

**M1.2 = Global Symbol Resolution + Early Lint（全局符号解析 + 早期拒绝）**
做到“Linker 成为唯一可信的结构裁判”的第二层：**在 emission 之前，把所有可判定的结构性错误都拒绝掉**，并且错误信息有可追溯的 origin 链。

> 这两件事在 v3 模型里分别对应：
>
> * “origin + diagnostics/SourceMap 的地基”（先不做完整 SourceMap，但要把 provenance 管线钉死）
> * “Stage 1：symbol resolution + early lint”

### 0.2 M1.2 的完成意味着系统具备

**Traceability（M1.2a）**

* 所有 IR 节点都携带 `origin=(module,file,line, …)`，并且 **任何 linker pass 都不会丢失 origin**
* 任意错误都能输出 **origin chain**（至少包含：generator callsite + unit + stmt/step + pass 名称）
* “冲突类错误”能同时报告 **双方 callsite**（例如符号冲突、重复定义等）

**Resolution & Lint（M1.2）**

* 构建全局 Symbol Table：`(origin, local_name, kind) → SymbolId`
* 全量 token 解析与校验：labels / math strings / proof tokens 都必须最终是 `SymbolRef[]`（COMPAT 除外）
* 早期拒绝（fail fast）至少覆盖：

  * 非 COMPAT 模式出现 raw string token
  * 引用未 export 的 `$a/$p`
  * 跨 unit 引用 `$f/$e`（hypothesis leakage）
  * 不存在或类型不匹配的 SymbolRef（例如 proof token 指向 Const/Var）

### 0.3 明确非目标（M1.2 不做）

* **不做完整 SourceMap（byte offset ↔ origin span）**：M1.2a 只做“origin 链 + 可追责诊断”的地基，SourceMap MVP 放在后续（Roadmap Phase 2）
* 不做 `$d` 推导（仍按当前策略：pass-through / linter-driven 以后再说）
* 不做 scope 合并优化、不做 proof compression、不做性能优化（这些都应在语义稳定后）

## 1. 输入与约束（硬规则）

### 1.1 Linker 的唯一真实输入

* **LIR（+可选 HIR）是唯一真实输入**，而不是 `.mm` 字符串
* 在 **默认模式（CI 默认）** 下：

  * math strings 与 proof tokens **必须**是 `SymbolRef[]`
  * 禁止 raw string token（除非显式 `COMPAT=on` 且 allowlisted）

### 1.2 Origin 必须是“强制字段”（M1.2a 的第一条铁律）

以下对象 **必须**携带 `origin`，缺一即 fail fast：

* `SymbolDef`
* `Statement`（每条 LIR stmt）
* `ProofUnit`
* （如有）HIR `Apply` step / proof step 元数据

> 备注：v3 已把 “origin/stmt_id/span_hint”写成工程必需字段（哪怕 span_hint 先是空壳）。M1.2a 的任务是把它从“建议”变成“强制不变量”。

---

## 2. 逻辑依赖图（把 M1.2a/M1.2 变成可执行骨架）

把里程碑拆成“不可逆依赖”：

1. **Origin Sealing（M1.2a）**
   → 2) **Diagnostic Object & Origin Chain（M1.2a）**
   → 3) **Global Symbol Table（M1.2）**
   → 4) **Token Resolution（M1.2）**
   → 5) **Early Lint（M1.2）**
   → 6) **Deterministic diagnostics snapshot tests（贯穿）**

其中 1) 与 2) 是“基础设施”，没有它们，3)-5) 的错误就会回落到“linker 内部 traceback”，失去工程意义（与 Roadmap 的“developer-grade debugging”目标冲突）。

---

## 3. 必须实现的 Pipeline（M1.2 的最小闭环）

下面按 v3 stage 的精神写，但 M1.2 的核心只聚焦 **Stage 0.5 + Stage 1**。

### Stage 0.5 — Provenance Sealing（M1.2a 核心）

**必须做到：**

* 在任何实质处理前运行 `origin_seal()`：

  * 遍历所有 IR 节点，检查 `origin` 非空且结构完整
  * 缺失则立刻报错（错误码固定、信息稳定），并指出“哪个节点/哪个 unit/哪个 stmt_id 缺 origin”
* 建立统一的 `Origin` 规范（推荐最小字段）：

  * `module_id`（Python import path 或你们的 module identity）
  * `file`（建议规范化为 repo 相对路径，避免机器差异）
  * `line`（1-based）
  * 可选：`function`/`callsite_digest`（用于去歧义）

**输出：**

* 一个“被封印的 IR”：从这一刻开始，pass 不允许产生无 origin 的新节点；如必须合成新节点，则 origin 必须有清晰规则（见 3.3）。

---

### Stage 1 — Global Symbol Resolution & Early Lint（M1.2 核心）

#### 3.1 构建全局 Symbol Table

**必须做到：**

* 按 v3：构建全局表
  `(origin, local_name, kind) → SymbolId`
* **冲突检测**（这点同时是 M1.2a 的“多 callsite 报告”验收点）：

  * 若同一 key 出现多个 `SymbolDef` → 报 `E_SYMBOL_COLLISION`
  * 错误必须包含：

    * 两个（或多个）定义点的 origin
    * 这些符号分别来自哪个 module/unit（如果可得）
    * 建议给出“如何修复”（例如：更改 local_name 或拆分 kind 或修正 origin identity）

**确定性要求：**

* 符号表遍历与分配必须排序（例如按 `(origin.module_id, origin.file, origin.line, kind, local_name)`），禁止依赖 dict/set 迭代顺序

#### 3.2 Token 解析（resolution）

**必须覆盖所有 token：**

* labels（`$f/$e/$a/$p` 的 label）
* math strings（typecode 与 expr token）
* proof tokens（RPN proof token stream）

**必须做到：**

* 默认模式下：任何 token 都必须是 `SymbolRef`（若出现 string → 直接 `E_RAW_TOKEN_FORBIDDEN`）
* 如果显式 `COMPAT=on`：

  * 允许 string token 进入 Stage 1，但必须在 Stage 1 内被解析成 `SymbolRef`（否则失败）
  * 且输出 IR 必须可标记“兼容路径被使用”（便于 CI shock therapy 与迁移追踪）

#### 3.3 早期 Lint（fail fast）

M1.2 的 lint 目标不是“推理正确”，而是把**结构性错误**尽可能早地拒绝，且能定位到 generator 调用点。

**必须做到（最低集合）：**

1. **No cross-unit hypothesis leakage**

   * proof tokens 不得引用其他 unit 的 `$f/$e` label（或等价的“内部假设符号”）
   * 报错需同时包含：

     * 引用点 origin（哪个 proof step/stmt）
     * 被引用 `$f/$e` 的定义点 origin

2. **No non-exported assertion reference**

   * 跨 unit 只能引用对方 `exports` 中的 `$a/$p`
   * 引用未 export 的 `$a/$p` → Stage 1 失败
   * 错误需包含“引用点 + 被引用 label 定义点 + 该 label 所属 unit 的 export 列表摘要（可选）”

3. **Raw token policy**

   * 非 COMPAT：string token 一律拒绝
   * COMPAT：必须能解析并输出 SymbolRef 化的 IR，同时留下可追踪标记（否则迁移无法收敛）

4. **Kind/type checking（强烈建议纳入 M1.2，而不是拖到后面）**

   * proof token 必须引用 Label-kind（并且是 `$a/$p` 这类“可用 assertion”，而不是 `$c/$v`）
   * math string token 必须是 Const/Var/Typecode（按你们的 symbol kind 模型）
   * 不匹配立即失败，避免把“明显坏 IR”留到 verifier 才爆

## 4. Traceability（M1.2a 的关键价值）

### 4.1 Origin Chain：最小可用标准

对任意 linker error，输出必须能回答：

> “这是哪个 generator 调用点产生的？
> 在 Linker 的哪个阶段、哪个 unit、哪个 stmt/step 被发现？”

**建议你们把诊断对象做成结构化数据（而不是只拼字符串）：**

* `error_code`
* `message`
* `primary_origin`（通常是“引用点”或“出错 stmt”）
* `related_origins[]`（例如冲突双方、被引用定义点）
* `origin_chain[]`（pass 上下文栈：`StageName → unit_id → stmt_id → step_idx → ...`）

这样测试可以对 JSON snapshot 做断言，避免因格式化变动导致脆弱测试。

### 4.2 “origin 生成规则”必须写死

当 linker pass 合成新对象时（例如“解析后的 token 列表”、或“合并/规范化的 stmt”），origin 的规则必须固定：

* **原则 A：不创造虚假来源**
  新节点应继承其输入节点的 origin，或采用“最靠近语义来源”的 origin（例如 proof step 的 origin 优先于 unit origin）。

* **原则 B：一眼能看懂**
  把“派生关系”放在 `origin_chain` 里，而不是伪造 file:line。

这与 v3 的“显式性 + 可诊断性”一致，也符合 Roadmap 的诊断闭环目标。

## 5. 验收标准（Definition of Done）

M1.2（含 M1.2a）完成，当且仅当：

1. ✅ **Origin sealing 生效**：任何缺 origin 的 IR 节点在 Stage 0.5 直接失败，错误稳定且可定位
2. ✅ **错误可追责**：任意 Stage 1 错误至少包含 generator callsite（origin）与 pass 上下文链
3. ✅ **符号冲突可双向定位**：`E_SYMBOL_COLLISION` 报告冲突双方 callsite
4. ✅ **早期拒绝集合完整**：raw token（非 compat）、跨 unit `$f/$e`、引用未 export `$a/$p` 均在 Stage 1 失败
5. ✅ **确定性**：同一输入触发同一错误时，诊断输出（结构化字段）稳定一致，不依赖 set/dict 随机顺序
6. ✅ **CI 默认 compat-off**：任何未经 allowlist 的 raw string token 引入都会让 CI fail

## 6. M1.2 测试完成目标（通过即验收）

建议把测试分成四类，沿用你们 M1.1 的风格，但突出“traceability + Stage 1”。

### A. Sanity Tests（回归护城河：M1.1 仍需全绿）

* **A0. `sanity_m11_*` 全部保持全绿**
  M1.2 不允许破坏 M1.1 已经建立的闭环（这是最重要的“不会倒退”约束）。

* **A1. `sanity_m12_symbol_resolution_smoke`**
  目标：最小 IR（1 unit）→ Stage 0.5/Stage 1 → 通过（不要求 verifier）
  断言：输出 IR 中不含 string token；SymbolRef 全可追溯到 SymbolDef。

### B. Golden Tests（确定性：诊断也必须可快照）

* **B1. `golden_m12_diagnostic_stable_snapshot`**
  目标：对固定错误输入跑两次，诊断对象（JSON/结构化字段）完全一致
  断言：`diag(run1) == diag(run2)`（建议 byte-identical JSON）

* **B2. `golden_m12_symbol_table_ordering`**
  目标：固定输入的符号表 key 排序与分配顺序稳定
  断言：输出的符号索引/映射快照一致（避免后续 relocation/emit 的隐性不稳定源头）

### C. Adversarial Tests（必须“早失败”，且能追责）

* **C1. `adv_m12_missing_origin_rejected_stage0`**
  目标：故意构造缺 origin 的 SymbolDef/Statement/ProofUnit → Stage 0.5 失败
  断言：错误码明确；错误包含哪个对象缺 origin（unit_id/stmt_id）；不进入 Stage 1

* **C2. `adv_m12_symbol_collision_reports_both_callsites`**
  目标：两个生成点制造同 key 的 SymbolDef → Stage 1 失败
  断言：错误包含两个 origin（双方 file:line 或 module:file:line）；诊断中 related_origins ≥ 2

* **C3. `adv_m12_forbid_raw_string_tokens_default_off`**
  目标：默认模式出现 string token → Stage 1 失败
  断言：错误包含 token 所在 stmt 的 origin；并明确提示“需要显式 COMPAT 才能通过”

* **C4. `adv_m12_forbid_cross_unit_hyp_leakage`**
  目标：proof 引用了另一个 unit 的 `$f/$e` → Stage 1 失败
  断言：错误同时包含引用点与被引用 `$f/$e` 的定义点 origin

* **C5. `adv_m12_forbid_non_export_label_reference`**
  目标：引用另一个 unit 未 export 的 `$a/$p` → Stage 1 失败
  断言：错误包含引用点与被引用 label 定义点 origin，并说明“non-exported”

### D. Structural Conformance Tests（中端不变量）

* **D1. `struct_m12_no_string_tokens_after_stage1`**
  目标：Stage 1 输出的 IR 中，labels/math/proof tokens 都是 SymbolRef
  断言：递归扫描 token payload，确保无 `str`

* **D2. `struct_m12_origin_chain_contains_pass_and_unit`**
  目标：任何 Stage 1 错误都必须带 pass 名称和 unit_id（至少在 origin_chain 中）
  断言：诊断结构化字段里可检索到 `Stage1` 与 `unit_id`

## 7. 实施建议（把工作拆成不互相踩踏的 PR）

为了降低回滚成本，建议按以下顺序落地（每一步都能被测试锁住）：

1. **引入结构化诊断类型（Diag）+ error_code 枚举**（先不改业务逻辑）
2. **实现 Stage 0.5 origin sealing**，并为“缺 origin”加 C1 测试
3. **把 linker pass 统一包装**：任何异常都被转换成 `Diag`，自动附加 pass 上下文（origin_chain）
4. **实现全局 symbol table + collision detection**（先做 C2 + B2）
5. **实现 token resolution + raw token policy**（做 C3 + D1）
6. **实现 export/hypothesis visibility lint**（做 C4/C5）

这条路径与 Roadmap 的“pass-based middle-end development + incremental verifiability”一致。

## 8. 一句话总结（给 agent 记住）

> **M1.2 的成功标准不是“能多链接”，
> 而是：Linker 的每一次拒绝都可追责、可复现、且发生得足够早。**
