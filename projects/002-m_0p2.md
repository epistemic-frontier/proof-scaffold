# M0.2 实现指南

本文档面向“重新设计并落地 linker_v1”的 **M0.2**：它不增加新的链接能力，而是把 **仓库约定、模块边界、开发入口与测试护栏** 固化下来，让新贡献者可以“一条命令跑通”，并让后续 M1.x 不再因为目录/入口/约定混乱而返工。

参考文档（实现时建议并排打开）：

* ProofScaffold 三层架构与信任边界（Design Notes Rev.2） 
* Link Model v4（linker_v1 入口规范与强不变量） 
* Roadmap & Methodology v2（M0.2 定义、验收、方法论） 
* Generator Design v2（Stage 0 的定位与前端/后端责任边界） 

---

## 1. M0.2 的定义与边界

### 1.1 目标

M0.2 只做两件事：

1. **仓库约定落地**
   代码布局、模块边界、命名规则、公共 API 面、内部实现区、测试分层，形成“写代码的人不需要猜”的一致结构。

2. **一条命令跑通新贡献者闭环**
   在干净环境里，执行一个命令即可完成：

   * 运行 M0.1 的 sanity（link → emit → verifier accept）
   * 运行一个小例子（最小可读、可定位、可重复）

这两点直接服务于 Roadmap 的原则：三层架构、信任边界、增量可验证与决定性。

### 1.2 非目标

M0.2 **刻意不做**：

* 不引入多模块 closure/toposort（Stage 4）
* 不做 relocation（Stage 6）或两段式 header 的完备策略演进（Stage 7 的完整形态）
* 不要求 DSL/Generator 大改（仅规定其位置与接口形状）
* 不实现 SourceMap/Debug Slice 的完整产物（但要在仓库结构中预留“不会再搬家”的槽位）

## 2. 从 v0 与 M1.4 失败中提炼出的 M0.2 硬约束

M0.2 的核心任务不是“把代码写出来”，而是“把未来必炸的结构性债务关在门外”。结合 Link Model v4 与现有诊断复盘，M0.2 必须把下面这些约定写死：

1. **公共 API 极小化**
   只暴露 `LinkerV1.link(...)` 与少量数据模型类型；所有 stage/passes 都放在 `internal/` 或 `passes/`，禁止外部直接 import。
   经验教训：v0 容易“到处 import 内部实现”，导致后续重构几乎等于重写。

2. **Stage 是一等组织单元**
   每个 Stage 一个模块文件，输入/输出类型明确，并在文件顶部写 pre/post conditions。
   经验教训：v0 里“功能长在一起”导致无法插入新的中间结果表，也无法做 determinism gate。

3. **决定性是仓库级约定，不是某个测试的偶然结果**
   所有“集合/字典/候选列表”都必须经由统一的排序工具输出；仓库约定里就要有“稳定排序函数放在哪里、按什么 key”。

4. **信任边界必须体现在目录结构上**
   verifier 是权威；linker 与 generator 不可信。仓库里要能一眼看出：

   * verifier 入口/封装在哪里
   * sanity harness 在哪里
   * 任何 linker 异常是否都被包装成 Diagnostic（不允许裸异常越界）

## 3. M0.2 的逻辑依赖图

M0.2 可以视作“工程与贡献者体验的链接器”：

```
已存在的 M0.1 最小闭环
  ├─ linker_v1 核心模块（diag/origin/symbols/stage1/emit）
  └─ tests: sanity + determinism

M0.2 在其上新增
  ├─ 统一 CLI 入口（一个命令跑通）
  ├─ examples/ 小例子（成功路径 + 可选失败演示）
  ├─ tests 目录分层与命名约定（golden / adversarial 预留）
  ├─ build/ 产物约定（临时 mm、伴随数据、日志）
  └─ CONTRIBUTING/README（最短路径指引）
```

## 4. 推荐的仓库布局与边界

### 4.1 顶层目录约定

建议把“文档、代码、示例、测试、生成物”明确隔离：

```
docs/                      # 规格、ADR、设计文档（可含你提供的四份文档的索引）
src/proof_scaffold/
  __main__.py              # M0.2: 统一 CLI 入口（一个命令跑通）
  verifier/                # verifier 封装（权威执行器接口）
  linker_v1/
    __init__.py            # 仅导出稳定 API
    api.py                 # LinkerV1.link(...)
    config.py              # LinkerConfig（compat / conformance / determinism policy）
    context.py             # LinkerContext（tables + stable sort helpers）
    diag.py                # Diagnostic + LinkerDiagError（稳定格式）
    origin.py              # OriginTable（确定性 intern）
    symbols.py             # SymbolDef + SymbolInterner（全局）
    ir_lir.py              # LIR 最小子集（M0.1 已有）
    unit.py                # ProofUnitIR
    passes/
      stage1_resolve.py
      stage7_emit.py       # 把 emit_mm.py 固化为 stage7_emit.py（更贴合 v4）
      _util_stable.py      # 稳定排序与 key 提取（M0.2 强制集中）
  generator/               # Stage 0 前端（可先放占位，不强迫 M0.2 全实现）
examples/
  minimal_ok.py            # 小例子：构造 IR -> link -> verify（成功）
  minimal_diag.py          # 可选：触发一个典型诊断（展示可读性与 origin）
tests/
  test_m0p1_sanity.py
  test_m0p1_determinism.py
  golden/                  # 固定输入 -> 固定输出（后续增长）
  adversarial/             # v4 ADV 测试骨架（M0.2 先建目录与 TODO）
build/                     # 运行时产物（gitignore）
```

说明：

* `verifier/` 必须独立出来，强化三层架构中的“权威执行器”。 
* `generator/` 作为 Stage 0 的落点必须在仓库里出现，即便 M0.2 只放接口与占位实现，也能锁定“DSL 只是前端”的心智模型。 
* `passes/` 下除了 stage 文件，还应有 `_util_stable.py` 这种“决定性工具集中点”，避免每个 stage 自己写排序规则，最后出现不一致。

### 4.2 公共 API 面约定

M0.2 要把“什么算公共”写死，建议：

* `proof_scaffold.linker_v1.api.LinkerV1`
* `proof_scaffold.linker_v1.config.LinkerConfig`
* 少量 IR 类型（`ProofUnitIR`, `LIRStmt` 等）

除此之外，`passes/*`, `context` 内部表结构、任何中间产物类型都视为 **内部实现**，默认不承诺稳定。

这样做的直接收益是：M1.x 大规模增 stage 时不会被外部调用绑死。

## 5. 一个命令跑通的 CLI 规范

### 5.1 设计原则

* 不依赖外部工程状态（不要求用户先手动下载某些 mm 文件）
* 不引入非决定性来源（时间、随机数、哈希迭代顺序）
* CLI 只做 orchestration：构造例子 → 调用 linker → 调用 verifier → 打印稳定输出

这符合“增量可验证”的方法论：任何新能力都要可一键验证。

### 5.2 推荐入口

> **Update**: `python -m proof_scaffold` is deprecated in favor of the `skfd` command. See `projects/003-skfd-kick-off.md`.

实现 `src/proof_scaffold/__main__.py` (Delegated to `skfd`)，提供最小子命令：

* `skfd smoke` (was `python -m proof_scaffold smoke`)
  运行：

  1. `check_sanity`（M0.1）
  2. `examples/minimal_ok.py`（M0.2 小例子）

* `python -m proof_scaffold sanity`
  仅运行 sanity（供 CI 或排查用）

* `python -m proof_scaffold example minimal_ok`
  仅运行一个例子（方便定位）

输出要求：

* 成功：打印 verifier “accepted” 的简短确认（不要打印长流）
* 失败：捕获 `LinkerDiagError` 并用其稳定格式打印（必须包含 `details` 与 origin）

## 6. 小例子应该长什么样

M0.2 的例子要满足两个目标：

1. “能读懂”：新贡献者看文件就知道 IR 是怎么构造的
2. “能对齐未来”：遵守 v4 的关键不变量（int tokens、全局符号空间、origin table）

### 6.1 minimal_ok 例子建议内容

建议例子 **仍用 M0.1 的最小可证程序**（`|-`, `ph`, `wph`, `th1`），但要在写法上更“像未来的项目”：

* 显式创建 `OriginTable`，把 `module_id` 设置为 `examples.minimal_ok`
* `UnitId` 固定，如 `examples.minimal_ok:unit0`
* 使用全局 `SymbolInterner` 分配 `SymbolId`
* LIR 中所有 tokens 是 `int`（SymbolId），不出现字符串 token 

例子文件只做两件事：

* `build_units() -> list[ProofUnitIR]`
* `run() -> None`：调用 `LinkerV1.link(units)`，并调用 verifier

### 6.2 minimal_diag 可选例子

提供一个“故意失败”的例子，用来展示诊断与 origin 链：

* 例如声明 local_name 以 `$` 开头，触发 `E_RESERVED_TOKEN_NAME`（Stage 1 早失败）
* 打印出来的错误必须稳定且包含 `details`（让贡献者一眼明白“为什么失败、在哪失败”） 

这不是验收必需项，但对新贡献者体验极其有价值。

## 7. 测试目录分层与命名约定

M0.2 不要求把 v4 的 adversarial suite 全实现，但必须把“未来要补什么”固定在仓库结构里，避免忘记。

### 7.1 测试分层

* `tests/test_m0p1_*`
  M0.1 的非协商测试：sanity + determinism（现有）

* `tests/golden/`
  固定输入 IR → 固定输出（byte-identical 或 token-identical）。
  M0.2 可先放空目录与 README，规定 golden 的写法与更新流程。

* `tests/adversarial/`
  对齐 Link Model v4 §10 的 ADV 清单。
  M0.2 目标是：把每条 ADV 用一个空测试文件占坑（或 xfail 标记 + TODO），并在文件头写明：

  * 对应 ADV 编号
  * 期望在哪个 stage 失败/成功
  * 要求的 diagnostic code

这会显著降低“以后补测试时才发现目录放错、依赖循环、fixture 不可复用”的成本。

### 7.2 测试命名规范

建议统一：

* Golden：`test_golden_<topic>__<case>.py`
* Adversarial：`test_adv_p0_1_global_id_space.py` 这种直接对应 v4 编号

## 8. 决定性与 CI 约定

M0.2 需要把“决定性”从“某个测试”升级为“仓库政策”。

### 8.1 必须固化的决定性政策

* 所有输出顺序由稳定 key 决定（例如 `SymbolKey = (origin_module_id, local_name, kind)`；`UnitId` 字典序；`StmtId` 升序） 
* 任何 `details` 中的列表都必须排序后写入（并且 `__str__` 渲染顺序稳定） 
* 禁止在 emission/diagnostic 中直接迭代 `set` 或无序容器
* 避免把对象 `repr`（含地址）写进输出；details 只能是 JSON 可序列化与稳定字段

### 8.2 CI 最小执行集建议

M0.2 应明确 CI 至少跑：

* `python -m proof_scaffold smoke`
* `pytest -q`（至少包含 M0.1 两条测试）

如果你们有 lint/typecheck，也可以作为附加项，但不应成为 M0.2 的交付阻塞。

---

## 9. 运行时产物与 build 目录约定

为了避免“写到处都是临时文件”，M0.2 必须规定：

* 所有运行时产物写入 `build/`（或 `./.build/`），并被 gitignore
* 产物命名稳定：

  * `build/sanity/out.mm`
  * `build/examples/minimal_ok/out.mm`
  * `build/.../diag.json`（如将 Diagnostic 同时输出 JSON）

即便 M0.2 不强制落盘（你们也可以全内存），只要落盘，就必须进这个目录。

这条约定对后续 SourceMap/Debug Slice 的落地至关重要：工具需要“有固定地方找伴随数据”。

## 10. M0.2 完成标准

M0.2 的 DoD 建议写成可勾选清单：

1. 仓库结构按约定落地

   * `verifier/`、`linker_v1/`、`examples/`、`tests/golden`、`tests/adversarial`、`build/` 均存在
2. `python -m proof_scaffold smoke` 可在干净环境中跑通

   * 先跑 sanity，再跑 minimal_ok
3. 公共 API 面最小化

   * `linker_v1/__init__.py` 只导出少量稳定对象
4. 决定性政策有唯一实现点

   * 存在 `passes/_util_stable.py` 或同等模块，供所有 stage/diag 复用
5. 测试目录分层完成

   * adversarial 目录至少有“占坑文件”与编号对齐说明（可以先 TODO/xfail）
6. 贡献者最短路径文档存在

   * README 或 CONTRIBUTING 里写明：安装、`smoke`、跑测试的命令

## 11. 紧接 M0.2 的自然演进路径

M0.2 做完后，M1.1/M1.2 的推进会更顺滑：

* M1.1 扩充 LIR statement model：直接在 `ir_lir.py` 增补类型与 lint，不需要搬目录 
* M1.2 引入更完整的 Stage 1 resolve+lint：在 `passes/stage1_resolve.py` 扩展即可，不会因为“谁在 import 谁”陷入重构
* Generator/DSL 的演进被锁在 `generator/`：前端改变不会污染 linker 内核边界
