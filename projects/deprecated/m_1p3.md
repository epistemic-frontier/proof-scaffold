# ProofScaffold — Agent Guide for M1.3（含依赖闭包 + 拓扑排序）

> 目标：把 Linker 从“能判结构、能早拒绝”推进到“**能计算依赖闭包、能确定性排序、能拒绝环与缺失依赖**”的工程状态，使多模块链接不再靠“碰运气的输入顺序”。

设计依据（本指引按这些文档的约束来写）：
   

---

## 0. Milestone Definition（先统一目标）

### 0.1 里程碑定义

**M1.3 = Dependency Closure + Topo Sort（依赖闭包 + 拓扑排序）**

要交付的最小闭环是：

1. **从已解析（resolved）的 proof tokens 中计算 `uses_assertions(T)`**（优先路径）
2. **构建 ProofUnit 的依赖图并进行确定性的拓扑排序**
3. **检测并拒绝 cycles（环）**
4. **在显式 COMPAT 构建下**，允许 `dependencies_hint=[...]` 作为“引导期兜底”，并且在缺失/错误时早失败；（可选）当 hint 与计算结果同时存在时进行对比

> v3 语义定位：
>
> * `uses_assertions(T)` 属于 “Proof Closure Contract（实现闭包）”，用来消除 ghost dependencies
> * 拓扑排序与环检测对应 v3 的 **Stage 4: Dependency resolution (closure DAG)**

### 0.2 M1.3 的完成意味着系统具备

**Closure 可计算、可检查**

* 对每个 theorem（以及任何包含 proof tokens 的 `$p`）都能抽取
  `uses_assertions(T) = { proof token 中出现的 `$a/$p` labels }`
* 闭包抽取以 **Stage 1 之后的 resolved tokens（SymbolRef）**为输入（不是 `.mm` 字符串），避免“字符串不可追责”的退化

**ProofUnit 可排序、可拒绝环**

* 能基于 `uses_assertions` 边构建 unit DAG，并确定性地产生一个 `units_linear_order[]`
* 如存在环，必须在 Linker 内部拒绝，并输出可追责的诊断（至少包括 cycle 中涉及的 unit origins，最好能指出形成边的 proof step）

**COMPAT 兜底可控**

* 仅在显式 COMPAT 构建中允许 `dependencies_hint` 兜底；缺失/错误必须 fail fast 且带 origin 链
* 这与“compat 是引导期工具、默认应关闭”的项目政策一致

### 0.3 明确非目标（M1.3 不做）

* **不做 ScopeFrames 规划与作用域隔离**（那是 M1.4）
* **不做 relocation / name mangling**（那是 M1.5）
* **不做两段式 emission（$c/$v header hoist）**（那是 M1.6）
* **不做完整 contract extraction**（`mandatory_hyps/mandatory_vars/dv_contract` 等属于后续 Phase 3；M1.3 只做 `uses_assertions` 的最小子集）

## 1. 输入与约束（硬规则）

### 1.1 Linker 的唯一真实输入（M1.3 的前置假设）

* M1.3 的输入是 **Stage 1 已完成后的 LIR ProofUnits**：tokens 已被解析为 `SymbolRef[]`
  （如果你们还保留 COMPAT 路径，也必须在进入闭包/拓扑之前完成解析或明确宣告“只能靠 hint 兜底”）

### 1.2 依赖边的合法来源（安全边界）

* v3 的防御性约束：**跨 unit 的依赖只能通过对方 exported `$a/$p` assertion**，不能窥视 `$f/$e`
* 换句话说：M1.3 的依赖图边应当“只由 `$a/$p` label 引用”诱导出来；一旦发现边源自 `$f/$e`，要么是 M1.2 没拦住，要么是 Stage 顺序/输入被绕开，应当直接 fail（并追责到 generator callsite）

### 1.3 确定性是硬约束（排序、诊断都要确定）

* v3 明确要求：**unit 的线性顺序必须是确定性的**
* Roadmap 也把 determinism 当作一等约束：排序、集合遍历、映射分配都必须稳定

### 1.4 Generator 侧配合（但不把它当 TCB）

* Generator 的职责边界里明确写了：外部依赖应当是显式的（至少可以作为 hint；理想情况下可由 proof tokens 推导）
* Linker 与 Python 生成逻辑都不在 TCB；正确性最终由 verifier 执行裁决

---

## 2. 逻辑依赖图（把 M1.3 拆成不可逆依赖）

把里程碑拆成“不可逆依赖链”：

1. **Export Index / Ownership Index（索引谁定义了哪个 label，哪个是 export）**
   → 2) **Closure Extraction：`uses_assertions`**（对 proof tokens 抽闭包）
   → 3) **Build DepGraph（unit → unit 边） + Missing-dep checks**
   → 4) **Deterministic Topo Sort（确定性排序）**
   → 5) **Cycle Diagnostics（环：给出可追责路径/至少给出相关 origins）**
   → 6) **Snapshot / Golden tests（排序与图结构必须稳定）**

其中 (1)–(3) 是排序的“事实基础”，(4)–(5) 是“线性化能力”，(6) 是“工程可复现”。

---

## 3. 必须实现的 Pipeline（M1.3 的最小闭环）

> 这里按 v3 stage 的精神描述：M1.3 实际覆盖 **Stage 2-lite（只做 uses_assertions） + Stage 4**。

### Stage 2-lite — Proof Closure Extraction（只抽闭包，不做完整 contract）

#### 3.1 建立 Label Ownership / Export 索引（前置）

**必须做到：**

* 建立 `label_id -> LabelInfo` 映射（至少包括）：

  * `def_unit_id`
  * `def_origin`（label 定义点）
  * `stmt_kind`（$f/$e/$a/$p）
  * `is_exported`（对 `$a/$p`：是否在 unit.exports 里）
* 该索引必须来源于 Stage 1 的解析结果（SymbolRef/Statement 信息），并且遍历顺序必须稳定

> 说明：M1.2 你们已有全局符号表与 “只允许跨 unit 引用 export” 的 lint；M1.3 不应再做一套“半吊子解析”，而是复用 resolved IR。
> （M1.3 可以在内部加 assert/defensive checks，确保没有绕过 Stage 1。）

#### 3.2 计算 `uses_assertions(T)`（优先路径）

**必须做到：**

* 对每个 theorem `T`（至少对每个 unit 的 exported `$p`，建议对所有含 proof 的 `$p`）扫描其 proof token list：

  * 若 token 对应 label-kind 且其 statement kind ∈ `{ $a, $p }` → 计入 `uses_assertions(T)`
  * 若 statement kind ∈ `{ $f, $e }` → **不计入 uses_assertions**（但可用作“引用点 provenance”）
* 这一定义与 v3 的 “Proof Closure Contract”一致：闭包只统计 proof 中出现的 `$a/$p` labels

**确定性要求：**

* `uses_assertions(T)` 的内部表示必须是稳定的（例如排序后的 list，而不是 set），排序键建议为：

  * `LabelInfo.def_unit_id` + `LabelInfo.def_origin` + `label_local_name`（或 `SymbolId` 的稳定序）
* 同一输入跑两次必须得到 byte-identical 的闭包快照（便于 golden tests）

#### 3.3 生成“依赖边的 provenance”（强烈建议纳入 M1.3）

为了让 cycle / missing-dep 的错误信息可追责，抽闭包时应同时记录：

* `edge: (user_unit_id, used_label_id)` 的“来源”：

  * `ref_origin`（哪个 stmt / proof step）
  * `ref_stmt_id`
  * （如有）`proof_step_idx`

这样在报错时能回答“是哪一个 proof token 造成了这个依赖边”。这符合你们 M1.2a 的 traceability 方向（虽然 M1.3 的 Roadmap 里没明写，但这是把错误做成 developer-grade 的关键）。

### Stage 4 — Dependency Resolution（closure DAG）+ Topo Sort（M1.3 核心）

v3 对 Stage 4 的描述非常直接：**用 `uses_assertions` 边做 ProofUnits 的拓扑排序，并检测/拒绝 cycles**。

#### 3.4 构建 ProofUnit 依赖图（DepGraph）

**必须做到：**

* 对每个 unit `U`，计算其外部依赖集合：

  ```
  deps(U) = { def_unit(label) | label ∈ uses_assertions(T), T 属于 U, 且 def_unit(label) != U }
  ```

* 对每条边 `U -> V`（U 依赖 V）要求：

  * `V` 必须存在于本次 link 的 ProofUnit 集合中，否则报 `E_MISSING_DEP_UNIT`
  * 该边必须是通过 `$a/$p` 诱导出来的（若发现通过 `$f/$e` 跨 unit 形成边，直接报 `E_HYP_LEAKAGE_DEP_EDGE` 或复用你们 M1.2 的错误码）

**诊断必须包含：**

* 引用点 origin（proof step 的 origin）
* 被引用 assertion 的定义点 origin
* 以及 “U 依赖 V” 的 unit_id 信息（用于快速理解 graph）

#### 3.5 确定性拓扑排序（Topo Sort）

**必须做到：**

* 使用确定性算法（Kahn 或 DFS 均可，但 tie-break 必须固定）生成 `units_linear_order[]`
* 当存在多个 in-degree=0 的候选节点时，必须使用稳定排序键选取顺序（建议：`(unit.origin.module_id, unit.origin.file, unit.origin.line, unit.unit_id)` 或 `unit.unit_id` 作为主键）

> 对外部可见行为：
> 同一输入的 `units_linear_order` 必须稳定，这将直接影响后续 M1.4 的 scope planning 与最终 emission 的可复现性。

#### 3.6 Cycle Detection（环检测）与诊断输出

**必须做到：**

* 如果 topo sort 不能消耗完所有节点 → 存在 cycle → `E_DEP_CYCLE`
* 错误信息至少要包含：

  * cycle 涉及的 unit 列表（稳定排序）
  * 每个 unit 的 origin（callsite）
* 强烈建议：输出一条可读的 cycle 路径（例如 `U1 -> U2 -> ... -> U1`），并为每条边附带 provenance（哪个 proof step 引用造成的边）。
  这会显著减少“我知道有环，但不知道怎么破”的调试成本。

---

### Stage 4.5 — COMPAT 兜底：`dependencies_hint`

Roadmap 对 M1.3 的 COMPAT 要求是：**显式 COMPAT 构建时允许 `dependencies_hint` 作为 bootstrap fallback；缺失/错误要早失败**。

**建议的工程化规则：**

* `dependencies_hint` 仅在以下情况下生效：

  1. 你们明确开启了 COMPAT（例如 `--compat` / `ALLOW_STRING_TOKENS=1`）
  2. 闭包无法从 proof tokens 计算（典型场景：interface-only build、或 proof 缺失）

* hint 的内容建议规范化为两种之一（任选其一并写死）：

  * **A. 以 unit_id 为粒度**：`dependencies_hint_unit_ids: list[UnitId]`
  * **B. 以 assertion label 为粒度**：`dependencies_hint_labels: list[LabelId]`（linker 再映射到 unit）

* 如果在 COMPAT 下需要 hint 但缺失 → `E_DEP_HINT_REQUIRED`

* 如果 hint 给出的依赖中存在“未知 unit/未知 label” → `E_DEP_HINT_INVALID`

* （可选但推荐）如果同时存在 `uses_assertions` 与 hint，且两者不一致：

  * CI/默认策略：直接失败 `E_DEP_HINT_MISMATCH`（避免悄悄引入 ghost dependencies）
  * 或者在工具链早期先做 “warning + 可升级为 error 的开关”。
    这点与 v3 “ghost dependency elimination” 的总体方向一致

## 4. Traceability（M1.3 必须继承 M1.2a 的价值）

M1.3 的新错误类型（missing deps / cycle）非常容易退化成“图算法报错”，所以必须强制：

* 所有错误都输出：

  * `error_code`（稳定）
  * `primary_origin`（通常选“引用边的 ref_origin”或“cycle 中的某个代表 unit 的 origin”）
  * `related_origins[]`（cycle 中各 unit origins；或 missing dep 的 def_origin / ref_origin）
  * `origin_chain[]`（必须包含 Stage 名与 unit_id；最好也包含 stmt_id/step_idx）

这与 “developer-grade debugging” 的目标一致：错误能映射回 *origin module → proof unit → statement → proof step* 的方向（SourceMap MVP 在后续，但现在就要保留可追责结构）。

## 5. 验收标准（Definition of Done）

M1.3 完成，当且仅当：

1. ✅ **闭包可计算**：对每个含 proof 的 theorem 能抽取 `uses_assertions(T)`（从 resolved proof tokens；非字符串流）
2. ✅ **依赖图可构建**：每个 unit 的外部依赖只来自 `$a/$p` 引用；任何缺失依赖在 topo 前 fail fast（带 origin）
3. ✅ **确定性 topo 排序**：同一输入得到稳定的 `units_linear_order`（不依赖 dict/set 遍历顺序）
4. ✅ **环检测可追责**：cycle 被拒绝，诊断中包含 cycle 相关 unit 的 origins（最好包含造成边的 proof step origin）
5. ✅ **COMPAT hint 有明确行为**：显式 COMPAT 下，缺失/错误 hint 会早失败并带 origin；非 COMPAT 下不接受 hint“悄悄成为默认”

## 6. M1.3 测试完成目标（通过即验收）

沿用你们在 M1.2 指引里的测试分层（Sanity / Golden / Adversarial / Structural），但聚焦“闭包 + 排序 + 环”。

### A. Sanity Tests（最小可用闭环）

* **A0. `sanity_m13_two_unit_topo_smoke`**
  构造两个 ProofUnit：`B` 的 proof 引用 `A` 的 exported `$a/$p`。
  断言：`units_linear_order == [A, B]`（严格顺序）

* **A1. `sanity_m13_uses_assertions_extraction_smoke`**
  对固定 proof tokens，断言 `uses_assertions(T)` 恰好包含预期的 `$a/$p` labels（且排序稳定）

### B. Golden Tests（确定性：排序与图都要快照）

* **B1. `golden_m13_topo_order_stable_snapshot`**
  同一输入跑两次：`order(run1) == order(run2)`（建议 byte-identical JSON）

* **B2. `golden_m13_depgraph_snapshot`**
  快照 `deps(U)` 邻接表（排序后）与每条边的 provenance（若实现了 3.3）以锁死确定性。

### C. Adversarial Tests（必须早失败、必须可追责）

* **C1. `adv_m13_cycle_detected_and_rejected`**
  构造 `A` 引用 `B`，`B` 引用 `A`。
  断言：报 `E_DEP_CYCLE`，diagnostic 至少包含 A 与 B 的 origins（最好包含造成依赖边的 proof step origin）

* **C2. `adv_m13_missing_dependency_fails_early`**
  构造 proof 引用了某 exported assertion，但其 defining unit 不在本次 link 输入集合。
  断言：报 `E_MISSING_DEP_UNIT`，包含引用点 origin 与被引用 label 信息（若可，包含 def_origin）

* **C3. `adv_m13_compat_hint_required_when_no_proof`**（COMPAT 专用）
  构造 interface-only unit（无 proof tokens），在 COMPAT 下不提供 `dependencies_hint`。
  断言：报 `E_DEP_HINT_REQUIRED` 且带 unit origin

* **C4. `adv_m13_compat_hint_incorrect_rejected`**（COMPAT 专用）
  hint 指向不存在的 unit/label，或漏掉必须依赖。
  断言：报 `E_DEP_HINT_INVALID` / `E_DEP_HINT_MISMATCH`（按你们选择）

### D. Structural Conformance Tests（中端不变量）

* **D1. `struct_m13_edges_only_from_assertions`**
  断言：DepGraph 的所有跨 unit 边都由 `$a/$p` 诱导（无 `$f/$e` 边）。

* **D2. `struct_m13_order_respects_deps`**
  对输出 order，断言：对任意边 `U -> V`，`index(V) < index(U)`。

## 7. 实施建议（把工作拆成不互相踩踏的 PR）

推荐按“先数据结构与可测闭包，再图，再排序，再 compat”的顺序落地：

1. **引入 Closure/DepGraph 的结构化数据模型**

   * `UsesAssertions{theorem_id -> [label_id...]}`
   * `DepGraph{unit_id -> [dep_unit_id...]}`
   * 先把快照测试框架搭起来（B 类）

2. **实现 `extract_uses_assertions()`（Stage 2-lite）**

   * 完成 A1 + B1/B2 的雏形

3. **实现 DepGraph 构建 + missing dependency 诊断**

   * 完成 C2

4. **实现确定性 topo sort + cycle detection**

   * 完成 A0 + C1（先保证“能拒绝”，再追求“输出 cycle path 更可读”）

5. **实现 COMPAT hint fallback +（可选）hint-vs-computed 对比**

   * 完成 C3/C4
   * 同时确保 compat 绝不成为默认路径（遵循 shock therapy 的治理逻辑）

---

## 8. 一句话总结（给 agent 记住）

> **M1.3 的成功标准不是“链接更多模块”，而是：Linker 能从 proof 真实引用中算出闭包，把 ProofUnit 以确定性顺序线性化，并在出现缺失依赖或环时给出可追责的拒绝。**
