## 0. Goals and Motivation

The source surface generated by the current semantic-v2 code generator has four problems:

1. assertion references are string indexes (`ASSERTIONS_BY_LABEL['mulcomd']`), preventing IDE
   navigation, completion, and checking;
2. hypotheses are accessed positionally (`proof.hypotheses[0]`), and intermediate step conclusions
   are invisible;
3. all proofs elaborate at import time (`PROOFS = {label: prove_x(), ...}`), making a four-domain
   import take 91 seconds;
4. assertion signatures render as nested constructor calls rather than conventional mathematical
   notation.

This project changes only the **generated source surface** (the public authoring shape of codegen
output) and the thin simplified interface it requires. It does not change the assertion-application
kernel, BuilderV2, the linker, or the verifiers.

Success criterion: for the same set.mm interval, a package generated with the new surface passes
every acceptance gate in Section 6, and its import cost is significantly lower than the eager
elaboration baseline.

## 1. Core Adjudications (All Closed)

### 1.1 Assertions Are Module-Level Bindings, and the Import Graph Is the Dependency Graph

- Every axiom, definition, and theorem MUST be a module-level Python binding in its owning module,
  with binding name = sanitized canonical label.
- All cross-module references use Python imports. String-index views (`SIGNATURES`, etc.) remain, but
  are reduced to read-only indexes **derived** from module bindings and are no longer sources of
  truth.
- The partition determines module ownership; its topological-order check (consumers must not precede
  dependencies) guarantees an acyclic module-level import graph.
- Same-module references use the module-level name directly, without an import.
- Every generated module MUST generate `__all__` containing only assertion-handle binding names in
  declaration order. `prove_*` proof functions remain module-level bindings (useful for tracebacks,
  coverage, and debugging), but are excluded from `__all__` and treated as non-public details under
  Python convention; the handle is the sole authoritative channel for the proof body.
- Derived string-index views filter module attributes by **type** (assertion handle), independent of
  naming.

### 1.2 Header and Local Import Rule

- **File headers may contain only**: `from __future__ import annotations`, public framework objects
  (`THEORY`, `Provable`, `ProofAuthor`/`CompleteProof` as needed for type annotations), and the
  standard library.
- **Every cross-module assertion reference is imported locally inside the proof function**,
  including same-package cross-module references and cross-package references.
- No frequency-based promotion into file headers (explicitly excluded; see Section 7).
- Generated file headers MUST contain a fixed comment explaining that local imports are an
  intentional choice supporting lazy elaboration.
- Ruff rule PLC0415 is disabled for generated packages (written into the generated package's Ruff
  configuration).

### 1.3 Theory Simplified Interface and Registration Semantics

- Add a read-only `Theory` simplified interface to `skfd.authoring` (new module, **additive only;
  existing kernel modules remain unchanged**) that binds language / calculus / catalog / assertion
  profile / upstream interface digests.
- A generated package's `_theory.py` instantiates `THEORY` and fixes upstream package interface
  digests (reject on error).
- Calling `THEORY.theorem(...)` / `THEORY.axiom(...)` / `THEORY.definition(...)` at module scope
  declares and registers an assertion in the package-level assertion catalog:
  - duplicate labels or assertion identifiers MUST reject on error;
  - registration order = build import order = partition order;
  - this is an explicit declaration call, not an implicit import side effect (within the boundary of
    Reference 011 invariant L1).
- `proof_id` is deterministically derived from the label and is not written explicitly in generated
  source.
- `THEORY` and the signature derive the `ProofAuthor` constructor arguments
  (calculus/catalog/profile/active_distinct); proof bodies do not repeat them.

### 1.4 Lazy Elaboration

- The `@<assertion>.proof` decorator only registers the proof-body callable; it **does not execute**
  it.
- Elaboration has only three trigger points: first access to `<assertion>.implementation`,
  `THEORY.verify_all()` (or an existing verification entry point), and `.mm` emission during a build.
- **Import never elaborates.** Proof-body errors therefore move from import time to verification/build
  time. This is an intentional behavior change and MUST be documented in the generated package
  README.
- Replace the `PROOFS` dictionary with a lazy read-only mapping view that elaborates on demand and
  caches `CompleteProof` values.

### 1.5 Unicode String Surface for Signatures and the Parse/Render Round-Trip Gate

- The default generated surface for premises / conclusions is **bare Unicode notation strings**
  (`premises=("φ → A ∈ ℂ", ...)`), converted into terms (`Term`) at the declaration boundary by a
  NotationSpec-driven parser.
- **Identity always resides in terms**: digests, equality, and the assertion catalog recognize terms
  only; strings are concrete syntax.
- Strings do not contain the judgment marker `⊢`; the provable judgment is expressed by parameter
  position (premises/conclusion).
- The low-level API also accepts `str | Term | Judgment`: the `Provable(...)` constructor remains in
  `notation.py` for handwritten use and facade fallback, but the default generated surface does not
  use it.
- The grammar uses minimal parentheses plus a versioned precedence table; precedence/associativity
  belong to generated `notation.py` (NotationSpec policy), not scattered conventions.
- **Parse/render round-trip gate**: the transpiler writes strings to source by calling `render()` on
  authoritative terms and simultaneously checks `parse(render(term)) == term`. A constructor that
  fails the round trip rejects on error; that assertion's signature falls back to the typed facade
  (constructor-call) form and is recorded in the generation report.
- Typed facade constructors remain available; `Provable` accepts both `str | Term`.

### 1.6 Order-Preserving Declaration of Schema Variables

- Schema variables are declared in `THEORY.theorem/axiom/definition` as
  `schema=("φ:wff", "A:class", "B:class", "C:class")`:
  - positional order = set.mm floating order, is ABI, and MUST NOT be regrouped by kind;
  - each item has format `"<display name>:<variable kind name>"`; the variable kind name maps to a
    language variable kind (`wff` / `setvar` / `class`);
  - the assertion owns each variable (the ownership discipline of Reference 012 §2.1).
- This set of declared variables is the parsing scope for string signatures; any undeclared variable
  rejects on error.
- When explicit substitution is needed, `subst` keys are display names (strings) of the applied
  assertion's schema variables, and values are notation strings or terms; the simplified interface
  converts them to the kernel's `Mapping[VariableRef, Term]`.
- Python binding identifiers use ASCII only (for example,
  `ph, A, B, C = x.schema_variables` when unpacking); Unicode appears only in strings and comments
  (characters such as `ℂ` collide with ASCII names under NFKC normalization).

### 1.7 Decorator Family

The first batch has only three entries. They are **interface policy/metadata and do not enter the
semantic digest**:

- `@<assertion>.proof`: the only decorator; registers a proof body (see 1.4). Decorator syntax is
  used only here (it decorates a real function);
- `deprecated="<reason>"`: a keyword argument of `THEORY.theorem/axiom/definition` (the assertion
  handle is an instance binding, so PEP 702 `@deprecated` does not apply and is therefore not used).
  Its data source is the set.mm `(New usage is discouraged.)` marker (with the Phase 2 fallback);
  references from `proof.use()` produce a warning-level diagnostic and are written into catalog
  metadata;
- `internal=True`: a keyword argument; excluded from the public manifest.

No other decorators or policy keywords may be added.

### 1.8 Step-Result Comments

- The generator renders each step conclusion computed by the kernel as an end-of-line comment;
  premises/conclusions using the string surface do not receive duplicate comments.
- Comments are derived, non-semantic data: regeneration recomputes them, they are never parsed back,
  and they do not enter digests.
- Truncation is deterministic: maximum line width is 100 columns, with overflow truncated using `…`.
- Codegen provides a `--no-step-comments` switch; comments are enabled by default.

### 1.9 Hypothesis and Proof-Function Naming

- Hypotheses are always unpacked as `h1..hN`, with rendered end-of-line comments. No semantic names
  are derived.
- Proof functions are always named `prove_<sanitized label>` rather than anonymous `_` (supporting
  tracebacks, profiling, and naming-consistency audits).

### 1.10 Name Sanitization and Collisions

- Retain the existing sanitization policy (for example, prefix names beginning with digits with
  `mm_`) and add complete checks against Python keywords and soft keywords.
- Collision scope: between sanitized labels; between assertion-handle names and every `prove_*`
  proof-function name (for example, a label `prove-x` sanitizing to collide with `prove_x`); with
  public framework names imported in the header (`THEORY`, `Provable`, etc.); and with `__all__` and
  dunder names. Every collision MUST fail generation and MUST NOT be silently renamed.

### 1.11 Manifest v2

- Retain the filename `transpiler-manifest.json`; the new schema is
  `mm-transpiler-manifest-v2`, adding the following to v1:
  - `semantic_interface_digests`: language / binding / calculus / catalog digests;
  - `notation_version`: notation policy version and digest;
  - `ownership`: an explicit mapping from label → dotted module path (formalizing v1 `modules`).
- When generating a downstream package, resolve cross-package import paths through `ownership` in
  the upstream manifest; missing data rejects on error.

### 1.12 Terminology and Naming Consistency

- All documentation, code identifiers, and filenames in this project MUST conform to
  [Terminology Specification 000](../references/000-terminology.en.md).
- New terms introduced by this project (see Section 8) MUST be registered in both the Chinese and
  English terminology specifications before implementation ends, or renamed and merged into
  existing terms.
- When an existing code name conflicts with the terminology table, do not rename it unilaterally;
  record it in the implementation report.

### 1.13 Make the Definition-Classification Policy Explicit

- The current heuristic "no premises and label begins with `df-` means definition" MUST move from
  pipeline code into the semantic profile as an explicit, versioned policy field.
- Behavior remains unchanged; only the location of the source of truth changes.

### 2.1 Theorem and Proof

```python
# metamath_numbers/complex/field_and_order.py
# GENERATED by mm-transpiler (semantic).
# Function-local imports are intentional: proof bodies elaborate lazily.
from __future__ import annotations

from skfd.authoring.proof_author import ProofAuthor
from skfd.authoring.assertion import CompleteProof

from metamath_numbers._theory import THEORY

__all__ = ["mulcan2d"]   # Assertion handles in declaration order; prove_* is excluded from __all__

# ── mulcan2d ─────────────────────────────────────────────────────────

mulcan2d = THEORY.theorem(
    "mulcan2d",
    schema=("φ:wff", "A:class", "B:class", "C:class"),
    premises=(
        "φ → A ∈ ℂ",
        "φ → B ∈ ℂ",
        "φ → C ∈ ℂ",
        "φ → C ≠ 0",
    ),
    conclusion="φ → ((A · C) = (B · C) ↔ A = B)",
    doc="Cancellation law for right-multiplication by a nonzero complex number.",
)

@mulcan2d.proof
def prove_mulcan2d(proof: ProofAuthor) -> CompleteProof:
    from metamath_logic.prop.equivalence import bitrd
    from metamath_numbers.complex.core import mulcand, mulcomd
    from metamath_set_theory.classes.equality import eqeq12d

    h1, h2, h3, h4 = proof.hypotheses      # h1: ⊢ φ → A ∈ ℂ …
    s1 = proof.use(mulcomd, h1, h3)        # ⊢ φ → (A · C) = (C · A)
    s2 = proof.use(mulcomd, h2, h3)        # ⊢ φ → (B · C) = (C · B)
    s3 = proof.use(eqeq12d, s1, s2)        # ⊢ φ → ((A·C) = (B·C) ↔ (C·A) = (C·…
    s4 = proof.use(mulcand, h1, h2, h3, h4)
    s5 = proof.use(bitrd, s3, s4)          # ⊢ φ → ((A · C) = (B · C) ↔ A = B)
    return proof.qed(s5)
```

Key points: no `REPLAYS`; no string labels; no positional hypothesis access; no elaboration during
import.

## 6. Acceptance Gates

- **G1 round-trip gate**: every signature in the slice satisfies
  `parse(render(term)) == term`; constructors falling back to the facade are listed in the report.
- **G2 frame-equivalence gate** (redefined 2026-07-19; rationale and details in 10.4; baselines remain
  unchanged—logic-domain baseline: the existing pipeline's logic `.mm` output; Phase 4 baseline:
  output from the default replay pipeline for the same interval):
  - **G2a (hard gate)**: after independently parsing the new-surface package's emitted `.mm` and the
    baseline, every assertion frame is equivalent (label sequence, typecode+expression, mandatory
    hypotheses, and distinct constraints all equal; hypothesis labels compared after positional
    normalization). The label-set/sequence clause is revised by Section 12: compare after removing
    the **mechanically derived exclusion set of derived syntax theorems** (details in 12.2);
  - **G2b (report only)**: compute a byte-for-byte diff against the baseline, classify and summarize
    differences in the generation report; byte identity is no longer a gate.
- **G3 verifier gate**: emitted `.mm` passes available independent verifiers (mmverify / reference
  Metamath / metamath-knife, following the verification process in the transpiler README; the report
  MUST list those actually run).
- **G4 determinism gate**: two clean generations are byte-identical (including the manifest).
- **G5 performance report** (report only; no hard budget): total signature-string parsing time,
  single-module import time, total package import time (new lazy surface versus eager-elaboration
  baseline), and complete generation time.
- **G6 toolchain gate**: `ruff check .`, `mypy .`, and `python3 -m pytest` are all green in both the
  proof-scaffold and transpiler repositories.

## 10. G2/G3 Blocker Adjudication (2026-07-19, All Closed)

This section provides normative adjudications for the three obstacles reported in §9.4 and has the
same standing as Section 1: **when an implementer encounters a decision point not covered by this
section, they MUST stop and report it and MUST NOT invent a decision.** The public interface shape in
this section is a frozen contract at the same level as Phase 0.

### 10.1 Path Adjudication: Adopt a General Emission Contract and Reject a Legacy Sidecar

- A general public contract named `emit_semantic_metamath_theory` **MUST** be added (retaining the
  name proposed in §9.4; location in 10.3).
- A legacy replay sidecar **MUST NOT** be used as the source of `.mm` emission. Rationale: a sidecar
  would give proofs a second source of truth and reduce semantic proof bodies to decoration,
  violating the single-source-of-truth discipline. Every `.mm` `$p` proof **MUST** be produced along
  the path lazy elaboration `CompleteProof` → `replay_proof` →
  `lower_replay_to_metamath_proof` → BuilderV2.
- Declaration-level emission data (`$c`/`$v`, floating `$f`, formation `$a`) is not proof content and
  **MAY** be derived by the transpiler during generation from the semantic profile and source
  database, then fixed in a versioned **emission binding** artifact (see 10.3). This is the same kind
  of data as the notation table: concrete syntax for language facts, and therefore not a violation
  of the preceding rule.

### 10.2 Boundary Clarification and Hypothesis-Root Support

The protected list in Section 4 comprises the assertion-application kernel,
`ProofAuthor.use()/qed()` semantics, BuilderV2, the linker, and the three verifiers.
`skfd.authoring.metamath_lowering` (and its `legacy_replay` re-export alias) is a backend **adapter
layer**, is not on that list, and is modifiable by this project under these constraints:

1. Make a **behavior extension** only (accept more valid inputs); output for existing valid inputs
   MUST NOT change.
2. Hypothesis-root support: when `plan.root_position` is a hypothesis position,
   `lower_replay_to_metamath_proof` **MUST** produce a valid `Proof` whose emitted `.mm` proof-token
   sequence is the **single-element sequence containing that hypothesis label** (the native proof
   form for set.mm `a1ii`: `a1ii $p |- ph $= a1ii.1 $.`).
3. This adjudication **explicitly permits** rewriting the existing hypothesis-root rejection test
   (the one `match="root to be the final"` occurrence in
   `tests/feature/test_assertion_application.py`) as a positive assertion. It is the only existing
   test that may be changed; all other tests have zero regressions.

### 10.3 Emission-Binding Artifact and `emit_semantic_metamath_theory` Contract

**skfd side** (proof-scaffold repository, additive only, new module
`src/skfd/authoring/metamath_emission.py`):

1. `MetamathEmissionBinding` (new read-only data class) carries declaration-level emission data:
   - constant/variable token tables (including token → emitted symbol name);
   - formation `$a` entries: label, typecode, expression-token sequence, and mandatory floating
     (sort, variable) sequence;
   - **interleaved emission sequence**: a complete ordered list interleaving formations and assertion
     labels in source order; the assertion labels MUST form a subsequence identical to catalog
     registration order, or reject on error;
   - sort → typecode mapping;
   - hypothesis-label policy version field (see item 3).
2. `emit_semantic_metamath_theory(theory, binding, ctx)`: emit declarations and assertions in the
   interleaved emission sequence; produce each `$p` proof through the semantic replay path required
   by 10.1. Per-assertion fields of `MetamathProofBinding` (`backend_label`, etc.) **MUST** be
   **mechanically derived** from theory and binding. If a derivable mapping is missing for any
   assertion, token, variable, or sort, **reject on error** and MUST NOT fill it heuristically.
3. Hypothesis-label allocation follows the default pipeline: a global `mmtranspiler.hN` counter,
   floating hypotheses (schema order) before essential hypotheses (premise order) for each assertion,
   and skipping reserved labels. This policy is written into the emission-binding artifact as a
   versioned field.

**transpiler side** (transpiler repository):

4. `semantic_package` generates `_emission.py` (fixing `MetamathEmissionBinding` data) and `build.py`
   (calling `emit_semantic_metamath_theory`).
5. Formation-entry labels come from the profile `formations` list; typecode, expression, and floating
   values are derived from the source database during generation. If a declaration named in profile
   `formations` is missing from the source database, or if the source interval contains a formation
   not covered by the profile, reject on error.
6. Manifest v2 additionally records `emission_policy_version` and the emission-binding digest; the
   G4 determinism gate covers `_emission.py` and `build.py`.

### 10.4 Rationale and Details for Redefining G2

The baseline `.mm` global numbering of `$f` labels (a `mmtranspiler.hN` counter shared across
modules) and exact proof-token order are **incidental implementation details** of the default
pipeline, not mathematical content. Reproducing those bytes from a semantic package would amount to
reimplementing legacy accidents, which is the wrong abstraction target. G2 is therefore changed (as
recorded in Section 6) to:

- **G2a frame-equivalence gate (hard gate)**: parse the baseline and new output with
  metamath-replay `Database` as an independent parser and require:
  - equal `$a`/`$p` label sequences, with the new-output label set equal to the baseline label set;
  - equal typecode + expression-token sequence for every assertion;
  - equal ordered mandatory `$e` expression sequences;
  - equal ordered mandatory `$f` (sort, variable) sequences;
  - equal sets of distinct-constraint pairs;
  - per-assertion positional normalization of hypothesis labels before comparison (the concrete
    `$e`/`$f` label text does not participate in the decision);
  - equal `$c` and `$v` sets.
- **G2b byte-comparison report (report only)**: classify and summarize a byte-for-byte diff in the
  generation report; expected residual differences are limited to hypothesis-label text and
  proof-token order categories.
- Comparator location: the transpiler repository (script or test); none of the checks may be relaxed
  merely to pass.

G3 is unchanged: independent verifiers (mmverify / metamath-knife, following the transpiler README
process, with actual runners listed in the report) remain authoritative for correctness.

## 12. G2a Derived-Syntax-Theorem Blocker Adjudication (2026-07-19, All Closed)

This section gives the normative adjudication for the `weq`/`wel` difference reported in §11.3 and
has the same standing as Sections 1 and 10: **when an implementer encounters a decision point not
covered by this section, they MUST stop and report it and MUST NOT invent a decision.**

### 12.1 Adjudication: Mechanically Exclude Derived Syntax Theorems; Reject Semantic Representation and Interval Changes

- **Definition (derived syntax theorem)**: a `$p` assertion in the source database whose result
  typecode belongs to semantic-profile `term_typecodes` (typecodes for language sorts) and does not
  belong to any `judgments[].typecode`. It is an abbreviation at the concrete-syntax layer whose
  complete content can be replayed from formation `$a` declarations (in the logic slice,
  `weq` = `cv`+`wceq` and `wel` = `cv`+`wcel`; set.mm comments also explicitly call them syntax
  proofs), and it carries no judgment-level mathematical content.
- **Reject** §11.3 option 1 (add a replayable semantic judgment/assertion representation): it would
  introduce a second judgment class into the calculus and affect the semantic boundaries of the
  assertion-application kernel, catalog, and three verifiers, exceeding the permitted modifications
  under the Section 4 protected list. It would also add no mathematical value to the already
  zero-difference `|-` content under frame equivalence. This direction becomes a separate candidate
  project (see 12.4).
- **Reject** the form of §11.3 option 2 that "changes the acceptance interval/baseline": `weq`/`wel`
  occur in the middle of the interval and cannot be excluded with `--start/--end`; manually editing
  baseline content would tamper with the baseline.
- **Adjudication**: the G2a label-set/sequence clause carries a **mechanically derived exclusion set**
  (12.2). The comparator computes the exclusion set automatically from baseline and profile; a label
  list **MUST NOT** be maintained manually, and the emission layer **MUST NOT** add a special case for
  any label (the final prohibition in §11.3 remains in effect).

### 12.2 Revised Details of the G2a Label Clause

All other G2a clauses (expressions, mandatory `$e`/`$f`, distinct constraints, `$c`/`$v`, and
positional normalization of hypothesis labels) remain unchanged.

1. The comparator MUST read the set of judgment typecodes (`judgments[].typecode`) and term
   typecodes (`term_typecodes`) from the semantic profile. The profile (versioned) is the source of
   truth for classification policy; the comparator MUST NOT hard-code typecode names.
2. **Exclusion set** := every `$p` label in the baseline whose result typecode ∈ term typecodes and ∉
   judgment typecodes. An empty exclusion set is valid.
3. Gates (all fail-closed):
   - `semantic output label set == baseline label set − exclusion set`;
   - `$a`/`$p` label sequences are positionally equal after removing the exclusion set from the
     baseline sequence;
   - semantic output **MUST NOT** contain any label in the exclusion set (the emission layer has no
     corresponding semantic object, so its presence means a special case was added);
   - comparison fails if any baseline `$p` result typecode belongs to neither term typecodes nor
     judgment typecodes (an unknown typecode MUST NOT be silently classified).
4. The generation report (as part of the G2b report) MUST record the exclusion set and each entry's
   label, typecode, and classification basis; any baseline-only or semantic-only label outside the
   exclusion set remains a hard failure.

### 14.1 Adjudication: Baseline Authority Resides in Emitted `.mm`, Not Packaging Metadata

   `.mm`. The complete command MUST be recorded in the report for reproducibility.

## 20. Stable Upstream Assertion Identity Seam (2026-07-24)

`Theory.theorem`, `Theory.axiom`, `Theory.definition`, and `Theory.primitive_rule` accept an additive
keyword-only `assertion_id: AssertionId | str | None = None`.

- `None` retains the existing `<theory namespace>#assertion:<label>` identity policy without changing
  compatibility behavior. In particular, a default primitive-rule signature retains its
  calculus-owned schema variables.
- An explicit value is reconstructed as an `AssertionId`; empty, malformed, duplicate, and
  upstream-conflicting identifiers fail closed. Canonical-label validation and local/upstream label
  collision checks remain independent and cannot be bypassed with an explicit identifier.
- Schema variables declared by theorem, axiom, and definition are owned by the resolved assertion
  identity. When a primitive rule receives an explicit identity, its complete signature is
  alpha-rebound to that identity: schema variables, premises, conclusion, and distinct-variable
  endpoints all use the new owner. The calculus rule itself is unchanged.
- Proof identity remains derived from the theory namespace and canonical label. This seam changes
  catalog/provider assertion joins, not the lazy proof-body registration or proof identity policy.

This permits generated providers to use an authoritative catalog identity such as `urn:uuid:...`
directly in the semantic handle while preserving handwritten and previously generated source that
omits the new keyword.

## 21. Predeclared Source-Order Registry Seam (2026-07-24)

`Theory.create` and `Theory.extend` accept an additive keyword-only
`declaration_order: Sequence[str] | None = None`.

- `None` preserves the existing registration-order behavior exactly.
- A supplied sequence is the complete allowed local assertion-label order. Empty or duplicate labels
  and registration of an unlisted label fail closed.
- `Theory.assertions` exposes the currently loaded subset in that predeclared order, independently of
  the order in which lazy provider shards were imported.
- `Theory.assertions_complete` reports whether the complete sequence has been registered.
  `Theory.verify_all()` rejects an incomplete configured theory before elaborating any proof.
- Assertion identity, proof identity, proof-body registration, and lazy elaboration are unchanged.

This seam lets ontology facades import arbitrary provider shards on demand while full verification,
derived catalog views, and Metamath emission retain the pinned source order deterministically.
